Module 1
Project Overview

What Is the Final Project?

The core askTake a real problem, make it run in parallel, optimize it, and analyze the performance you obtained.

It is open-ended on purpose: you choose the application and the parallel programming model. What stays fixed is the engineering discipline — a baseline, a parallel version, and an honest measurement of the difference.

Three valid shapes Accelerate — speed up a problem with parallel programming.
Reproduce — re-implement a parallel algorithm / high-performance result from a research paper.
Survey — review a parallelism / performance topic. Not recommended.

Team Size & Expectations

Single-personYou scope, build, and analyze the whole project yourself.
Two-person teamAllowed — at most two students. More work is expected from a team.
Plan for the team factorIf you pair up, the scope should be visibly larger — e.g. more optimizations, more platforms compared, or a deeper analysis. Split the work so each person owns a clear part.

Implementation Rules

LanguageRestricted to C or C++.
Parallel modelNo restriction — multithreading (OpenMP, Pthreads), GPU (CUDA, OpenCL), or distributed (MPI, Hadoop, Spark).
MachinesUse ARC or Hazel. Mind the available resources.
Pick the model that fits the problem Shared-memory loops → OpenMP / Pthreads. Massively data-parallel kernels → CUDA. Problem too big for one node → MPI. Match the tool to where the parallelism actually lives.
Module 2
Suggested Topics

General Directions

AccelerateUse parallel programming to speed up a problem you care about.
ReproduceRe-implement a parallel algorithm / high-performance result from a published paper.
SurveyA literature survey on a parallelism / performance topic. Not recommended.
Best bet The "accelerate" and "reproduce" tracks give you real code to benchmark — which is what the report and grade reward. Choose one of those unless you have a strong reason not to.

Potential Topics

ThemeWhat you might do
Accelerating DL / ML modelsSpeed up training or inference; combine with pruning, sparsification, or quantization.
Accelerating data analyticsAnalyze healthcare / social-media data with a method, then parallelize that method; or speed up data reorganizing, rearranging, cleaning.
Improving fundamental operationsLinear algebra, tensor algebra, matrix solvers — exploit data features like sparsity, symmetry, or non-negativity.
Pattern Each theme is "a real workload + a method to parallelize." Pick a workload, find the hot computation, and make that parallel.

Other Acceptable Topics

Performance modelingModeling a parallel algorithm's performance is fine on its own.
Profiling / analysisOK — but must come with at least one optimization driven by what you found.
BenchmarkingAcceptable — must compare multiple cases, scenarios, or platforms.
I/O optimizationI/O-focused optimization work is acceptable.
Common thread Even the "analysis-flavored" topics must end in something concrete — an optimization, a comparison, or a model — not just observations.

Writing the Final Report

Format4 pages excluding references, ACM 2-column template. Submit the code alongside it.

A typical structure: problem & motivation → baseline & method → parallel design → experimental setup → results (speedup / scaling) → analysis & conclusion.

Show, don't claim Include the things a reader needs to believe you: • machine & thread/GPU/node counts
• baseline timing & how you measured
• speedup and a scaling plot
• what the profiler said you fixed
Module 4
Tips for a Good Project

Pick Something Measurable

Define the metric firstDecide up front what "better" means — runtime, throughput, speedup, or scaling efficiency — and how you will measure it.

A project you can put a number on is a project you can defend. Avoid scopes where success is fuzzy ("it feels faster").

Scope realisticallyOne application, one clear hot spot, on ARC or Hazel. A small problem done thoroughly beats an ambitious one with no results.

Baseline First, Then Profile

Workflow 1. Correct serial baseline + timing.
2. Profile to find the hot spot.
3. Parallelize / optimize that spot.
4. Re-measure; verify results still correct.
5. Sweep threads / cores / problem size.

Never optimize before you have measured. The profiler, not intuition, tells you where the time goes.

Show Speedup & Scaling

Speedup \( S_p = T_1 / T_p \) — serial time over parallel time on p workers.
Strong vs. weak scalingStrong: fixed problem, more workers. Weak: grow the problem with the workers.

Amdahl's law caps strong scaling by the serial fraction — expect curves to bend, and say why.

Plot measured vs. ideal; explain the gap.

Common Pitfalls to Avoid

No baselineSpeedup is meaningless without a correct, timed serial reference.
Wrong answers, fastAlways verify the parallel output matches the baseline.
Single data pointOne thread count tells you nothing — sweep p and problem size.
Over-scopingToo ambitious → no results. Narrow it so you can finish and measure.
Optimizing blindTuning before profiling wastes effort on cold code.
Late startLeaving experiments to the last week leaves no room to debug.

Final Project — Big Picture

ChooseA real C/C++ workload to accelerate or a paper to reproduce.
BuildBaseline → profile → parallelize with OpenMP / CUDA / MPI on ARC or Hazel.
