Module 1
Performance Metrics

Why Study Performance?

It's the whole pointPerformance is the driving motivation for going parallel — we must justify the effort with measured gains.

Performance reasoning shows up everywhere: algorithm design, architecture design, and system building, purchase & evaluation.

Goals of optimization Shorter overall execution time
Better speedup
Better scalability

Define how you will measure before you optimize — otherwise you can't tell whether a change helped.

Why Can't We Just Get a Speedup of p?

With p processing elements, the dream is to cut execution time by a factor of p — linear speedup. Most programs can't reach it.

Limited by serial parts Software: algorithm limits, inherently sequential phases.
Hardware: architecture limits, memory bandwidth limits.
Over-achievers existSuper-linear speedup (speedup > p) is real — usually from a cache/memory effect: more PEs means more aggregate fast storage, so the working set fits.

Also from exploratory decomposition (a parallel search finds the answer early).

Metric: Execution Time

TS — best serial timeTP — parallel time on p PEs

The most straightforward metric: elapsed (wall-clock) time from the start of computation to when the last processing element finishes.

Parallel overheadThe total work spent beyond the serial computation:
\( T_o = p\,T_P - T_S \)
Charging for usageCenters bill in service units:

SUs = #processors
      × wall_time
      × priority_level

You pay for all allocated processors for the whole wall time — idle PEs cost money.

Metric: Speedup

\( S_p = \dfrac{T_S}{T_P} \)
Fair baselineTS must be the time of the best sequential algorithm — not your parallel code run on one PE.

Ideal is Sp = p (linear). Reporting against a slow serial baseline inflates speedup dishonestly.

Most real curves fall below the diagonal.

Metrics: Efficiency & Cost

EfficiencyFraction of time a PE is usefully employed — the ratio of actual to ideal performance.
\( E = \dfrac{S_p}{p} = \dfrac{T_S}{p\,T_P} \)

E = 1 is perfect (linear); typical programs sit below 1.

CostResource usage = processor-time product:
\( C = p \times T_P \)
Idle time still billsLoad imbalance hurts twice: it raises TP and charges idle PEs. Watch where speedup stops scaling.

If speedup is 14 on 16 PEs but only 20 on 32 PEs, doubling the PEs barely helped — cost nearly doubled for ~40% more speedup. Efficiency = cost-efficiency.

Module 2
Amdahl's Law

Amdahl's Law — Fixed Problem Size

Split the work into a fraction f that can be parallelized and (1-f) that is inherently serial. On p PEs:

\( S = \dfrac{1}{(1-f) + \dfrac{f}{p}} \)
The ceilingAs p → ∞, the parallel term vanishes:
\( S_{\max} = \dfrac{1}{1-f} \)
Brutal arithmeticIf just 5% is serial (f = 0.95), you can never beat S = 20×, no matter how many PEs you throw at it.
serial 1−fSmax
10%10×
5%20×
1%100×
0.1%1000×

Amdahl's Law — the Curves

Each curve flattens toward its ceiling 1/(1−f). Adding PEs past the knee buys almost nothing.

Amdahl's Law in Reality

Even worse than the curveAmdahl is an upper bound. Real programs fall below it because parallelization itself is not free.

The model assumes the parallel fraction divides perfectly across PEs with zero coordination cost. It never does.

TakeawayAttack the serial fraction first — it sets the ceiling. Then attack the overhead (Module 4) — it pulls you below the ceiling.
Module 3
Gustafson's Law & Scaling

Strong vs. Weak Scaling

Strong scalingFix the problem size, add PEs. Goal: finish the same work faster. This is the world Amdahl describes — the serial part caps you.
Weak scalingGrow the problem with p (fixed work per PE). Goal: solve a bigger problem in the same time. This is the world Gustafson describes.
Why both matter Programs must accommodate growth in two dimensions — problem size and number of PEs. A method great at strong scaling can stall at weak scaling, and vice-versa.

Gustafson's Law — Scaled Speedup

Gustafson's insight: in practice we grow the problem to fill bigger machines, so the serial fraction shrinks relative to the larger parallel part. With serial fraction s on p PEs:

\( S_{\text{scaled}} = s + p\,(1-s) = p - s\,(p-1) \)

Speedup now grows roughly linearly with p — no fixed ceiling.

Amdahl vs. Gustafson Same hardware, different question:
Amdahl — fixed work, "how much faster?"
Gustafson — fixed time, "how much bigger?"
No contradictionThey model different experiments. Amdahl bounds strong scaling; Gustafson rewards weak scaling.

Worked Example: Summing n Numbers on p PEs

Each PE locally sums n/p values, then the partials merge in a tree of depth log p (a step each direction).

\( T_P = \dfrac{n}{p} + 2\log p \)
\( S = \dfrac{n}{\frac{n}{p} + 2\log p} = \dfrac{n\,p}{n + 2p\log p} \)
\( E = \dfrac{n}{n + 2p\log p} \)
Larger n ⇒ higher efficiency at the same p.

Isoefficiency — How Big Must the Problem Grow?

Write efficiency with total overhead To(W,p) and problem size (work) W:

\( E = \dfrac{1}{1 + \dfrac{T_o(W,p)}{W}} \)

To hold E constant as p grows, W must rise to keep To/W fixed:

\( W = K \cdot T_o(W,p) \)

W(p) is the isoefficiency function — the growth needed to keep efficiency constant.

Reading it W(p) ≤ O(p) ⇒ scalable (work grows ≤ linearly)
W(p) = O(p²) ⇒ poorly scalable
Summing example Overhead To = 2p\log p, so
\( W = K\cdot 2p\log p \)
slightly worse than linear ⇒ fairly scalable.
Module 4
Sources of Overhead

Parallelization Is Not Free

Interaction — "talking"Inter-process communication & synchronization. Sources: data exchange, barriers, locks.
Idling — "waiting"Load imbalance, serialization, resource contention. A PE sits idle while others work.
Excess computation — "replicating"Work repeated by multiple processes that the serial program did once.
All of it counts These add up to To = p\,TP − TS. Every unit of overhead drags efficiency below 1 and pulls real speedup below the Amdahl bound.

Load Imbalance & Synchronization

Load imbalanceParallel time is set by the slowest PE. Uneven work ⇒ everyone waits at the barrier for the laggard.

Fixes: finer decomposition, dynamic / guided scheduling, work-stealing, or partitioning by estimated cost rather than count.

Communication Cost: the α/β Model

Two-part costSending an m-byte message costs
\( t_{\text{msg}} = \alpha + m\,\beta \)

α = per-message latency (startup); β = per-byte transfer cost.

α dominatesα is larger than β by a factor of several thousand. Latency, not bandwidth, kills fine-grained codes.
Optimization ideaSend fewer, bigger messages. Combine (aggregate) communication to amortize the fixed α over many bytes.

The key health metric is the computation-to-communication ratio: more compute per byte moved ⇒ overhead becomes negligible.

Case Study: Matrix Multiply — Ratio Matters

The kernel

for (i=0; i<n; i++)
  for (j=0; j<n; j++) {
    C[i][j] = 0;
    for (k=0; k<n; k++)
      C[i][j] += A[i][k] * B[k][j];
  }

Naive: per element of C, fetch one row of A and one column of B — two messages of size n.

\( \text{ratio} = \dfrac{2n}{2(\alpha + n\beta)} = \dfrac{n}{\alpha + n\beta} \)

α=1000, β=0.2, n=1000 ⇒ ratio = 0.83 (communication-bound!).

Block itCompute a g×g tile of C from bunches of g rows / columns. Same two messages now carry far more reuse.
\( \text{ratio} = \dfrac{2g^2 n}{2(\alpha + g\,n\beta)} = \dfrac{g^2 n}{\alpha + g\,n\beta} \)

Same α, β, n with g=10 ⇒ ratio = 33.3.

40× betterBlocking raised compute-per-byte ~40×, turning a comm-bound kernel into a compute-bound one — without changing the math.
Module 5
Profiling & Tracing Tools

Profiling vs. Tracing

ProfilingAggregate "where does time go?" — per-function/loop time & counts. Two ways to collect:
Sampling (low overhead, statistical) vs. instrumentation (exact, intrusive).
TracingTime-ordered "when did events happen?" — a timeline of communication, sync & idle across PEs. Big logs, but reveals imbalance & serialization.
Golden rule Measure, don't guess. Profile first to find the hot loop, then trace to see why the parallel version stalls there.

The Toolbox

ToolKindWhat it's for
gprofprofiler (sampling + call counts)Classic per-function time & call graph; -pg at compile.
Intel VTuneprofiler (HW sampling)Hotspots, microarchitecture, memory & threading analysis.
Valgrind (Callgrind/Cachegrind)instrumentation (simulation)Exact call counts & cache-miss modeling; also memory errors.
PAPIHW-counter APIPortable access to counters (cycles, cache misses, FLOPs) from your code.
Score-P + Vampir/Scalascatracing & profilingMPI/OpenMP timelines, communication patterns at scale.

Many tools build on PAPI underneath to read the CPU's performance counters.

Reading Counters & a Quick gprof Pass

gprof workflow

gcc -O2 -pg prog.c -o prog
./prog               # writes gmon.out
gprof prog gmon.out > report.txt

The flat profile ranks functions by self-time; the call graph shows who called the hot one.

PAPI: count cache misses

int ev[2] = { PAPI_L2_TCM,
              PAPI_TOT_CYC };
long long val[2];
PAPI_start_counters(ev, 2);
kernel();              // region of interest
PAPI_stop_counters(val, 2);
// val[0] = L2 misses, val[1] = cycles
Mind the overhead Instrumentation (Valgrind, -pg) can slow code 10–100×; sampling profilers (VTune) stay near native speed. Profile a representative run, not a toy input.

Performance — Big Picture

MeasureS = TS/TP, E = S/p against the best serial baseline.
BoundAmdahl caps strong scaling at 1/(1−f); Gustafson rewards weak scaling.
ScaleIsoefficiency says how fast work must grow to keep efficiency.
Trim overheadBalance load, raise compute-to-communication ratio, send fewer/bigger messages.
VerifyProfile to find the hot spot; trace to see why it stalls — gprof, VTune, PAPI, Score-P.
One sentence Shrink the serial fraction, kill the overhead, grow the problem when you add PEs — and never optimize what you haven't measured.
