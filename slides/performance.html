Module 1
Performance Metrics

Why Study Performance?

It's the whole pointPerformance is the driving motivation for going parallel — we must justify the effort with measured gains.

Performance reasoning shows up everywhere: algorithm design, architecture design, and system building, purchase & evaluation.

Goals of optimization Shorter overall execution time
Better speedup
Better scalability

Define how you will measure before you optimize — otherwise you can't tell whether a change helped.

Why Can't We Achieve Linear Speedup?

With p processing elements, the dream is to cut execution time by a factor of p — linear speedup. Most programs can't reach it.

Limited by serial parts Software: algorithm limits, inherently sequential phases.
Hardware: architecture limits, memory bandwidth limits.
Over-achievers existSuper-linear speedup (speedup > p) is real — usually from a cache/memory effect: more PEs means more aggregate fast storage, so the working set fits.

Also from exploratory decomposition (a parallel search finds the answer early).

Performance Metrics at a Glance

\(T_S\) — best serial time\(T_P\) — parallel time on p PEs
MetricDefinitionWhat it tells you
Execution time\(T_S,\ T_P\)wall-clock: best serial vs. parallel on p PEs
Speedup\(S_p = T_S/T_P\)how many× faster — ideal \(S_p = p\)
Efficiency\(E = S_p/p\)fraction of a PE usefully used — ideal \(1\)
Cost\(C = p \times T_P\)processor-time product — what you're billed
Overhead\(T_o = p\,T_P - T_S\)total extra work beyond the serial computation
Scalabilitytrend of \(S_p,\ E\)do they hold as p (& problem) grow? (Amdahl / Gustafson)
The through-lineEvery metric is a function of just two times, \(T_S\) and \(T_P\). We define each next, then bound them with Amdahl & Gustafson.

Metric: Execution Time

\(T_S\) — best serial time\(T_P\) — parallel time on p PEs

The most straightforward metric: elapsed (wall-clock) time from the start of computation to when the last processing element finishes: \(T_S\) and \(T_P\).

It's the max, not the sumParallel time is set by the slowest PE — one straggler and everyone waits. That's why load balance matters.
Charging for usageCenters bill in service units:

SUs = #processors
      × wall_time
      × priority_level

You pay for all allocated processors for the whole wall time — idle PEs cost money. The priority/charge factor is site-specific.

Metric: Speedup

\( S_p = \dfrac{T_S}{T_P} \)
Fair baseline\(T_S\) must be the time of the best sequential algorithm — not your parallel code run on one PE.

Ideal is \(S_p = p\) (linear). Reporting against a slow serial baseline inflates speedup dishonestly.

Super-linear speedup Extra hardware advantage exploited by parallelization:
  • Better utilization of faster storage (cache, memory)
  • Exploratory decomposition
Most real curves fall below the diagonal.

Metric: Efficiency

EfficiencyFraction of time a PE is usefully employed — the ratio of actual to ideal performance.
\( E = \dfrac{S_p}{p} = \dfrac{T_S}{p\,T_P} \)

\(E = 1\) is perfect (linear); real programs sit below 1 and fall as \(p\) grows — overhead takes a bigger share.

Efficiency = cost-efficiencyIt's speedup normalized by the resources you paid for. High speedup at low efficiency means you're burning PEs for diminishing returns.

14× on 16 PEs (\(E\approx0.88\)) → 20× on 32 PEs (\(E\approx0.63\)): double the machine for ~40% more speedup — efficiency tells you it wasn't worth it.

Metrics: Cost & Overhead

CostResource usage = processor-time product:
\( C = p \times T_P \)
Idle time still billsLoad imbalance hurts twice: it raises \(T_P\) and charges idle PEs. Watch where speedup stops scaling.
Parallel overheadTotal work spent beyond the serial computation:
\( T_o = p\,T_P - T_S = C - T_S \)
Cost buys overheadSubtract the useful serial work \(T_S\) from the total processor-time \(C\); what remains, \(T_o\), is pure overhead — communication, idle time, redundant work.

Module 1 — Review

1. Against which serial time is speedup measured, and why does it matter?

Against the best sequential algorithm's \(T_S\). Otherwise you could fake a big speedup by comparing against a bad serial baseline.

2. A program gets speedup 20 on 32 PEs. What is its efficiency?

\(E = S/p = 20/32 = 0.625\) — about 63% of the machine is doing useful work.

3. Express efficiency in terms of cost.

\(E = T_S / C\), where \(C = p\,T_P\).

Module 2
Scalability

Scalability

Two dimensions must grow Parallel programs need to accommodate growth in two dimensions:
  • Problem size
  • Number of processing elements
Scalability Capacity to increase speedup in proportion to the number of processing elements.

More Definitions

Problem size
  • Amount of computation in solving the problem
  • Basic steps of computation in best sequential algorithm
    • Not just data size
  • Correlated with serial execution time
Scalable parallel systems Able to maintain efficiency by simultaneously increasing number of processing elements and problem size.

Strong vs. Weak Scalability

Two ways to talk about "scaling to more PEs" — they differ in what you hold fixed as p grows.

Strong scaling Fixed total problem size; add PEs to finish the same work faster.
  • Work per PE shrinks as p grows
  • Overhead's share rises → efficiency falls
  • Governed by Amdahl → bounded speedup
Weak scaling Fixed work per PE; grow the problem with p, holding time roughly constant.
  • Total problem size grows with p
  • Efficiency can be held ≈ constant
  • Governed by Gustafson → near-linear speedup
Tie it together Amdahl → strong scaling (fixed size, bounded speedup); Gustafson → weak scaling (grow the problem, near-linear speedup). Isoefficiency (later this module) makes the weak-scaling question — how fast must the problem grow to hold efficiency? — precise.

Amdahl's Law

Amdahl's law Let s = the serial fraction of the work; the remaining \(1-s\) splits across \(p\) processors:
\( S(p) \;=\; \dfrac{1}{\,s + \dfrac{1-s}{p}\,} \)
As \(p \to \infty\) the second term vanishes, leaving the ceiling
\( S_{max} \;=\; \dfrac{1}{s} \)
  • s = 0 ideal — linear, follows the diagonal
  • s = 0.01 caps at 100× (plot ≈ 50 at p = 100)
  • s = 0.2 caps at just 5×, no matter how many PEs

Even a tiny serial fraction puts a hard ceiling on speedup.

Amdahl in Reality

Even after accounting for the serial part, real speedup peaks, then declines.

Amdahl's law assumes the only cost is the serial fraction. But adding PEs adds more than zero overhead:

  • Communication grows with p
  • Synchronization & idling grow with p
  • Eventually overhead outweighs the extra compute
Past the sweet spot Adding processors can make a program slower. Knowing where the curve peaks is half of performance engineering.

Gustafson's Law (Scaled Speedup)

Amdahl fixes the problem size and asks how much faster p PEs run it. Gustafson flips the question: in practice we buy more PEs to solve a bigger problem in the same time.

Setup Let the parallel work grow with p so the parallel time is fixed at \(T_P = 1\), split into a serial slice s and a parallel slice 1 − s.
Scaled speedup
\( S(p) \;=\; s + p\,(1-s) \)
Speedup grows nearly linearly with p — the serial fraction only lowers the slope, it does not cap the result.
Amdahl — fixed problem Serial fraction s is fixed → \(S \le 1/s\), a hard ceiling no matter how many PEs you add.
Gustafson — scaled problem The problem grows with p → \(S = s + p(1-s)\) keeps rising with p, limited only by the serial slice.
  • \(s = 0.05,\ p = 32\): \(S = 0.05 + 32(0.95) \approx 30.5\)
  • …versus Amdahl's ceiling of \(1/s = 20\) for the same serial fraction

Same s — opposite outlook. The difference is entirely what you hold fixed: the problem, or the work per PE.

Isoefficiency — How Big Must the Problem Grow?

Efficiency is useful work over total processor–time. Write \(W = T_S\) (problem size = useful work); the cost \(p\,T_P\) splits into useful work plus overhead:

\( E = \dfrac{S}{p} = \dfrac{T_S}{p\,T_P} = \dfrac{W}{p\,T_P} \)

Since \(T_o = p\,T_P - T_S\), the cost is \(p\,T_P = W + T_o(W,p)\), so

\( E = \dfrac{W}{W + T_o} = \dfrac{1}{1 + \dfrac{T_o(W,p)}{W}} \)

To hold \(E\) constant as \(p\) grows, \(W\) must rise to keep \(T_o/W\) fixed:

\( W = K \cdot T_o(W,p) \)

W(p) is the isoefficiency function — the growth needed to keep efficiency constant.

W(p) ≤ O(p) ⇒ scalable (work grows ≤ linearly)
W(p) = O(p²) ⇒ poorly scalable
Summing example Overhead \(T_o = 2p\log p\), so
\( W = K\cdot 2p\log p \)
slightly worse than linear ⇒ fairly scalable.

Example: Summing n Numbers on p PEs

Decompose: spread the n numbers evenly across PE 0 … PE p−1.

  • Each PE owns a contiguous block of n / p numbers
  • This is a simple data decomposition
Two phases ahead Each PE first sums its own block (a local sum), then the PEs merge the local sums into one global sum.

Summing: The Algorithm

  • Local sum: each PE adds its n/p numbers → cost n / p
  • Tree merge: combine local sums pairwise up a binary tree → cost 2 log p
Parallel time
\( T_P \;=\; \dfrac{n}{p} \;+\; 2\log p \)
Why the 2? Each of the \(\log p\) tree levels costs 1 communication (receive the partner's partial sum) + 1 addition — communication is counted, each at one time unit. With free communication it would be just \(\log p\).
First term shrinks with p; second term grows with p — that tension is the whole scalability story.

Summing: Speedup

Speedup
\( S \;=\; \dfrac{n}{T_P} \;=\; \dfrac{np}{\,n + 2p\log p\,} \)
  • Larger n stays closer to linear for longer
  • Small n = 64 plateaus near 5 — overhead dominates quickly
Lesson For a fixed problem, more PEs eventually stop helping. To keep scaling, you must also grow n.

Summing: Efficiency

Efficiency
\( E \;=\; \dfrac{S}{p} \;=\; \dfrac{n}{\,n + 2p\log p\,} \)
  • All curves decline as p grows (overhead 2p log p in the denominator)
  • Bigger n stays near 1.0 longer
The fix To hold efficiency constant, grow n as you grow p. How much? → isoefficiency.

Module 2 — Review

1. State Amdahl's law and the maximum speedup for s = 0.05.

Max speedup \(S = 1/s\). For s = 0.05, \(S = 1/0.05 = 20\)× — no matter how many PEs.

2. What is "problem size W" — is it the data size?

No — W is the amount of computation: the basic steps of the best sequential algorithm. It correlates with serial execution time.

3. State the isoefficiency relation and what W(p) ≤ O(p) means.

\(W = K\,T(W,p)\). If W only needs to grow linearly (or less) with p to hold efficiency, the system is scalable.

Module 3
Sources of Overhead

Parallelization Is Not Free

Interaction — "talking"Inter-process communication & synchronization. Sources: data exchange, barriers, locks.
Idling — "waiting"Load imbalance, serialization, resource contention. A PE sits idle while others work.
Excess computation — "replicating"Work repeated by multiple processes that the serial program did once.
All of it counts These add up to \(T_o = p\,T_P - T_S\). Every unit of overhead drags efficiency below 1 and pulls real speedup below the Amdahl bound.

Load Imbalance & Synchronization

Load imbalanceParallel time is set by the slowest PE. Uneven work ⇒ everyone waits at the barrier for the laggard.

Fixes: finer decomposition, dynamic / guided scheduling, work-stealing, or partitioning by estimated cost rather than count.

Communication Cost: the α/β Model

Two-part costSending an m-byte message costs
\( t_{\text{msg}} = \alpha + m\,\beta \)

α = per-message latency (startup); β = per-byte transfer cost.

α dominatesα is larger than β by a factor of ~103–104 (network-dependent). Latency, not bandwidth, kills fine-grained codes.
Optimization ideaSend fewer, bigger messages. Combine (aggregate) communication to amortize the fixed α over many bytes.

The key health metric is the computation-to-communication ratio: more compute per byte moved ⇒ overhead becomes negligible.

Case Study: Matrix Multiply

How would we parallelize this? Start with the serial triple-nested loop:

Serial matmul — C = A × B

for (i = 0; i < n; i++)
  for (j = 0; j < n; j++) {
    C[i][j] = 0;
    for (k = 0; k < n; k++)
      C[i][j] += A[i][k] * B[k][j];
  }

Each element C[i][j] needs row i of A and column j of B.

The questions
  • How do we distribute A and B?
  • How large is the overhead?
  • How much does a message / remote access cost?

A Simple Dynamic Algorithm

  • Distribute A by rows, B by columns
  • Any processor can request a row of A or a column of B (two messages)
  • Distribute the work of computing each element of C via a load-balancing scheme
Bonus Dynamic load balancing works even on heterogeneous machines — fast PEs naturally grab more work.
But how much does it cost? To answer "how large is the overhead?" we need a model of communication, then a computation–communication ratio — measured per PE, for the unit of work it grabs (one element of C, quantified on the next slide):
\( \dfrac{\text{useful compute}}{\text{communication}} \)
High ratio = compute-bound (good). Low ratio = communication-bound (bad).

Ratio: The Simple Dynamic Algorithm

Cost to compute one element of C:

  • Computation = 2n (one + and one * per k; 1 unit time each)
  • Communication = two messages of size n = \(2(\alpha + n\beta)\)
\( \text{ratio} \;=\; \dfrac{n}{\alpha + n\beta} \)
Plug in numbers \(\alpha = 1000,\ \beta = 0.2,\ n = 1000\):
\( \dfrac{1000}{1000 + 1000\cdot 0.2} = \dfrac{1000}{1200} \approx 0.83 \)
Ratio < 1 → communication-bound. We move two whole vectors just to do 2n flops. Bad.

A Better Algorithm: Blocking

Store A as row-bunches (g rows each) and B as column-bunches. Each object computes a g × g section of C.

  • Computation = \(2\,g\,g\,n\) ops
  • Communication = 2 messages, \(g\,n\) bytes each
\( \text{ratio} \;=\; \dfrac{g^2 n}{\alpha + g n\beta} \)
Plug in numbers \(\alpha = 1000,\ \beta = 0.2,\ n = 1000,\ g = 10\):
\( \dfrac{10^2\cdot 1000}{1000 + 10\cdot 1000\cdot 0.2} = \dfrac{100000}{3000} \approx 33.3 \)
From 0.83 → 33.3: a 40× better ratio. Now compute-bound.
Why it works Larger blocks → higher arithmetic intensity → the fixed message cost \(\alpha\) is amortized over far more compute.

Module 3 — Review

1. Name the three sources of parallel overhead.

Inter-process interaction (talking), idling (waiting), and excess computation (replicating).

2. Why does the simple dynamic matmul give a ratio of only 0.83?

Per element it does just 2n flops but ships two n-element messages: \(n/(\alpha + n\beta) = 1000/1200 \approx 0.83\) — communication-bound.

3. How does blocking raise the ratio to 33.3?

A g×g block does \(g^2 n\) flops per pair of messages: \(g^2 n/(\alpha + gn\beta)\). Bigger blocks amortize \(\alpha\) over more compute → higher arithmetic intensity.

Profiling & Tracing Tools

Profiling vs. Tracing

ProfilingAggregate "where does time go?" — per-function/loop time & counts. Two ways to collect:
Sampling (low overhead, statistical) vs. instrumentation (exact, intrusive).
TracingTime-ordered "when did events happen?" — a timeline of communication, sync & idle across PEs. Big logs, but reveals imbalance & serialization.
Golden rule Measure, don't guess. Profile first to find the hot loop, then trace to see why the parallel version stalls there.

Tools

Reading Counters & a Quick gprof Pass

gprof workflow

gcc -O2 -pg prog.c -o prog
./prog               # writes gmon.out
gprof prog gmon.out > report.txt

The flat profile ranks functions by self-time; the call graph shows who called the hot one.

PAPI: count cache misses

int ev[2] = { PAPI_L2_TCM,
              PAPI_TOT_CYC };
long long val[2];
PAPI_start_counters(ev, 2);
kernel();              // region of interest
PAPI_stop_counters(val, 2);
// val[0] = L2 misses, val[1] = cycles
Mind the overhead Heavy instrumentation (Valgrind) can slow code 10–100×; -pg/gprof is much lighter (~1.1–2×); sampling profilers (VTune) stay near native speed. Profile a representative run, not a toy input.

Performance — Big Picture

Measure\(S = T_S/T_P\), \(E = S/p\) against the best serial baseline.
BoundAmdahl caps strong scaling at 1/(1−f); Gustafson rewards weak scaling.
ScaleIsoefficiency says how fast work must grow to keep efficiency.
Trim overheadBalance load, raise compute-to-communication ratio, send fewer/bigger messages.
VerifyProfile to find the hot spot; trace to see why it stalls — gprof, VTune, PAPI, Score-P.
One sentence Shrink the serial fraction, kill the overhead, grow the problem when you add PEs — and never optimize what you haven't measured.
