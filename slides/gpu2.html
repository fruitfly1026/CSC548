Part B
Scheduling Threads — Warps & the SM

The Streaming Multiprocessor (SM)

SM streaming multiprocessor SP streaming processor (CUDA core)
A GPU is an array of SMs
  • Each SM contains many streaming processors (SPs)
  • One or more warp schedulers
  • Shared memory / L1 and a register file, all on-chip
Blocks are assigned to SMs; threads run as warps.
UIUC ECE498/AL & NVIDIA CUDA C Programming Guide.

The Warp — Unit of Scheduling

warp = 32 threadswarpSize built-in
What a warp is
  • 32 threads from one block, with consecutive threadIdx
  • Run on the same SM
  • The unit of thread scheduling — hardware schedules warps, not threads
Zero-overhead warp scheduling
  • Only one warp executes at a time
  • Warps whose next instruction's operands are ready are eligible
  • Eligible warps selected by priority
  • All 32 threads execute the same instruction (SIMT)

Interleaving Warps Hides Latency

When a warp stalls on a long-latency op (e.g. a global load), the scheduler switches to another ready warp — for free. The SM stays busy.

Key ideaGPUs hide latency with parallelism instead of reducing it with caches.
UIUC ECE498/AL.

Branch Divergence

All 32 threads of a warp share one program counter. If threads take different branches, the hardware runs both paths with lane masking.

divergent branch in a warp

if (threadIdx.x < 16) {
    // path A — lanes 0..15 active,
    //          lanes 16..31 masked off
    x = doA();
} else {
    // path B — lanes 16..31 active,
    //          lanes 0..15 masked off
    x = doB();
}
CostNot all ALUs do useful work while a path runs — the masked lanes idle.
Worst caseA fully divergent 32-thread warp serializes all 32 paths — as low as 1/32 of peak throughput.
No divergence cost if all 32 lanes take the same branch. We revisit divergence as an optimization lever in Part H.

In-class: Counting Warps

Q1A GT200 SM hosts 1024 threads. How many warps?
A: \( 1024 / 32 = 32 \) warps.
Q23 blocks × 256 threads — how many warps?
A: \( 3 \times 256 / 32 = 24 \) warps.
Q3A warp is 32 threads but an SM has only 8 SPs — what gives?
A: 8 threads enter the SPs per cycle, so it takes 4 cycles to dispatch a full warp.

In-class: Warps to Hide Latency

SetupA kernel has 1 global read (200 cycles) followed by 4 non-dependent mul/add ops. How many warps are needed to hide the read latency?
Work it out
  • Each op takes 4 dispatch cycles → 4 ops = \( 4 \times 4 = 16 \) cycles of independent work per warp
  • We must cover \( 200 \) cycles: \( 200 / 16 = 12.5 \)
  • Round up: \( \lceil 12.5 \rceil = \) 13 warps

The CUDA Memory Model

Memory Hierarchy

UIUC ECE498/AL & NVIDIA CUDA C Programming Guide.

Registers

Per-thread, fast on-chip. The register file is split across all resident threads — so register use caps occupancy.

G80 budgetPer SM: 768 threads & 8K registers → \( 8192 / 768 = 10 \) registers/thread available.
Spill example
  • 11 regs × 256-thread blocks → \( 11 \times 256 = 2816 \) regs/block
  • \( 8192 / 2816 = 2 \) blocks → 512 threads → 16 warps
  • Fewer warps → less latency hiding
Special registersthreadIdx · blockIdx · blockDim · gridDim

Local Memory

What it is
  • Register / array spill space
  • Physically lives in global memory (off-chip)
  • Addressing resolved by the compiler
  • Stores are cached in L1 on SM 2.x+
Performance
  • Hurts via extra memory traffic + instruction count
  • But L1-contained spills are not always bad

Shared Memory

Per-block, fast on-chip, full-speed random access — the programmer-managed scratchpad.

G80 budgetPer SM: 16 KB shared, up to 8 blocks → \( 16/8 = 2 \) KB/block if fully occupied.
Occupancy exampleIf each block uses 5 KB → \( 16 / 5 = 3 \) blocks per SM (shared memory is the limiter).
This is the leverShared memory is what makes tiled matmul (Part E) fast — threads in a block cooperatively stage data on-chip.

Global & Constant Memory

Global memory
  • Long latency — 100s of cycles, off-chip
  • G80 86.4 GB/s, GT200 150 GB/s, up to 4 GB
  • Reads cached on 2.x+; writes invalidate the cache
Constant memory
  • Short latency / high bandwidth when all threads read the same location
  • Cached
  • Up to 64 KB

Part D
Synchronizing Threads

__syncthreads() — Block Barrier

A barrier within a block: a thread waits until all threads in the block reach the call before any continues.

classic barrier pattern

Mds[i] = Md[j];      // each thread loads
__syncthreads();     // wait for ALL loads
func(Mds[i], Mds[i+1]);   // now safe to read
                          // a neighbor's value
Use it whenThreads in a block produce data (into shared memory) that other threads in the same block will consume.
GuaranteeAfter the barrier, every shared-memory write made before it is visible to all threads in the block.

Barrier Walkthrough

Warps reach the barrier at different times; all continue only once the last warp arrives.

Same execution time helpsThreads doing similar work reach the barrier together → little waiting.
Only within a blockCross-block sync would break transparent scalability — blocks must run in any order, on any number of SMs.

Hazard: Conditional Barriers Deadlock

A barrier requires every thread in the block to reach it. Putting it inside a branch that only some threads take → the rest never arrive → hang.

deadlock — barrier in only one branch

if (cond) {
    __syncthreads();   // BAD: only some
}                      // threads reach it
fix — a barrier in BOTH branches

if (cond) {
    __syncthreads();   // all threads
} else {
    __syncthreads();   // reach a barrier
}
RuleEither all threads in the block execute a given __syncthreads(), or none do.
Part E
Tiled Matrix Multiply

Naive Multi-block Matmul

Each thread computes one element of P by streaming an entire row of M and column of N from global memory.

CUDA C — naive kernel

int col = blockIdx.x*blockDim.x + threadIdx.x;
int row = blockIdx.y*blockDim.y + threadIdx.y;
float pValue = 0;
for (int k = 0; k < width; k++)
    pValue += devM[row*width + k]
            * devN[k*width + col];
devP[row*width + col] = pValue;
CUDA C — launch

dim3 dimBlocks(TILE_WIDTH, TILE_WIDTH);
dim3 dimGrid(WIDTH/TILE_WIDTH,
             WIDTH/TILE_WIDTH);
MatrixMultiplyKernel
    <<<dimGrid, dimBlocks>>>(...);

The Bandwidth Bottleneck

Every pValue += does 2 global loads (4 B each) for 2 FLOPs — far too much memory traffic.

G80 numbers
  • Peak compute: 346.5 GFLOPS
  • That would need 1386 GB/s of bandwidth
  • But memory bandwidth is only 86.4 GB/s
ResultMemory caps you at \( \approx \) 21.6 GFLOPS (and ~15 in practice) — about 4% of peak.
FixWe must cut global-memory access — reuse data on-chip via shared memory.

The Tiling Idea

Break P into TILE_WIDTH × TILE_WIDTH tiles — one tile per block. Each phase:

  • Load a tile of M and a tile of N into shared memory
  • __syncthreads() — wait for the loads
  • Accumulate the partial dot product from the tiles
  • __syncthreads() — before overwriting the tiles next phase
UIUC ECE498/AL.

Tiled Kernel

CUDA C — shared-memory tiled matmul

__shared__ float sM[TILE_WIDTH][TILE_WIDTH];
__shared__ float sN[TILE_WIDTH][TILE_WIDTH];
int bx = blockIdx.x;  int by = blockIdx.y;
int tx = threadIdx.x; int ty = threadIdx.y;
int col = bx*TILE_WIDTH + tx;
int row = by*TILE_WIDTH + ty;
float pValue = 0;
for (int m = 0; m < width/TILE_WIDTH; m++) {        // m = phase index
    sM[ty][tx] = devM[row*width + (m*TILE_WIDTH + tx)];
    sN[ty][tx] = devN[col + (m*TILE_WIDTH + ty)*width];
    __syncthreads();                                 // 1: tiles fully loaded
    for (int k = 0; k < TILE_WIDTH; ++k)
        pValue += sM[ty][k] * sN[k][tx];
    __syncthreads();                                 // 2: done before overwrite
}
devP[row*width + col] = pValue;
Two barriers#1 after the loads so every thread sees the full tiles; #2 so no thread overwrites the tile before others finish reading it. width/TILE_WIDTH = number of phases.

▶ Demo: Demos/cuda/04_matmul.cu

Choosing TILE_WIDTH

Bounded by max threads/block (G80/GT200 = 512, Fermi+ = 1024) and shared memory per block.

G80 shared-memory limit
  • 16 KB/SM, ≤ 8 blocks → 2 KB/block
  • \( 16 \times 16 \times 4\,\text{B} = 1 \) KB each for sM, sN → 2 KB
  • So TILE_WIDTH = 16
  • Larger tile → fewer resident blocks
Payoff
  • Each value reused TILE_WIDTH times → global access cut by 16×
  • G80 now supports 345.6 GFLOPS — near the 346.5 peak

First-order Sizing

TILE_WIDTH = 16
  • \( 16 \times 16 = 256 \) threads/block
  • A \( 1024 \times 1024 \) output P → \( 64 \times 64 = 4096 \) blocks
  • Each block does 512 global loads (per phase, both tiles) for 8192 mul/add
Bottom lineCompute now dominates memory — the global-memory bandwidth is no longer the limiter. Tiling turned a 4%-of-peak kernel into a near-peak one. Next we push further with architecture-aware optimizations.

Part G
Parallel Reduction Revisited

Parallel Reduction — Sum 8 Elements

Reduce array [0,1,2,3,4,5,6,7] to its sum (28) by a binary tree: each pass halves the live data.

3 passes for 8 elements; in general \( \log_2 n \) passes. UIUC ECE498/AL.

Reduction — Interleaved Version (stride 1, 2, 4)

CUDA C — interleaved reduction

unsigned int t = threadIdx.x;
for (int stride = 1; stride < blockDim.x; stride *= 2) {
    __syncthreads();
    if (t % (2*stride) == 0)
        partialSum[t] += partialSum[t + stride];
}
Thread view
  • Pass 1 (stride 1): threads 1,3,5,7 idle — only n/2 threads do work
  • Pass 2 (stride 2): only threads 0,4 active
  • Pass 3 (stride 4): only thread 0 active
Problem The active threads are spread out (0,2,4,6 …). Number active halves each pass, but they sit in every warp.

Reduction — Contiguous (Tweaked) Version (stride …4, 2, 1)

CUDA C — contiguous reduction

unsigned int t = threadIdx.x;
for (int stride = blockDim.x/2; stride > 0; stride /= 2) {
    __syncthreads();
    if (t < stride)
        partialSum[t] += partialSum[t + stride];
}
Thread view
  • Active threads are the low-index, contiguous ones: 0…stride−1
  • Pass 1: threads 0–3; Pass 2: 0–1; Pass 3: 0
  • Can launch half the threads/blocks and load two elements each
Why it matters Idle threads cluster together → whole warps go idle → warps retire early (next section).

What's the Difference?

Same arithmetic, same result. Only the branch condition and the stride order change.

Interleaved — stride 1, 2, 4

for (stride = 1; stride < blockDim.x; stride *= 2){
  __syncthreads();
  if (t % (2*stride) == 0)
      partialSum[t] += partialSum[t+stride];
}
Contiguous — stride 4, 2, 1

for (stride = blockDim.x/2; stride > 0; stride /= 2){
  __syncthreads();
  if (t < stride)
      partialSum[t] += partialSum[t+stride];
}
The one line if (t % (2*stride) == 0) vs. if (t < stride) — the contiguous condition keeps active threads packed, which we'll see is hugely better for the warp scheduler.
Part H
Warp Partitioning & Divergence

Warp Partitioning

warp 32 threads executed in lockstep (SIMT) warpSize threads per warp (32 on NVIDIA)

Warp partitioning = how a block's threads are divided into warps. Recall from Part B that divergence within a warp runs both paths with lane masking — here we use partitioning to avoid it.

Goals
  • Minimize divergent branches
  • Retire warps early to free SM clock cycles
Rule Threads are partitioned by consecutive, increasing threadIdx (after row-major linearization for 2D/3D).

Partitioning 1D, 2D, 3D Blocks

1D block
  • Warp n = threads 32n … 32n+31
  • Last warp padded if block size not a multiple of 32
  • Fermi+: up to 1024 threads/block
2D block (e.g. 64×8)
  • Linearize row-major: increase threadIdx.x first within row y=0, then next row
  • Warp0 = (x0–31, y0)
  • Warp1 = (x32–63, y0)
  • Warp2 = (x0–31, y1) …
3D block
  • Start at z=0
  • Partition that plane as 2D
  • Then increment z and repeat
KeyDivergence is a property within a warp — threads in different warps never "diverge" from each other. A branch that splits exactly on a warp boundary (e.g. threadIdx.x > warpSize-1) costs nothing; one splitting inside a warp (e.g. threadIdx.x > 15) diverges.

Part I
Memory Coalescing

Memory Coalescing — Which Access Pattern?

A matrix is stored row-major in global memory. Each thread iterates over the matrix. Which pattern does the hardware like?

(a) Column after column Within one load iteration, each thread reads consecutive addresses across threads.
(b) Row after row Within one load iteration, adjacent threads read strided addresses (one full row apart).
Answer: (a) is coalesced ✓ We want the threads active in a given load iteration to touch contiguous memory. The GPU then fuses a full warp's reads into one transaction.

Why Coalescing — DRAM Bandwidth

The GPU coalesces consecutive reads from a full warp into one wide read. Peak bandwidth needs large consecutive requests.

GPU generationPeak DRAM bandwidth
G8086.4 GB/s
GT200150 GB/s
Fermi192 GB/s
Kepler240 GB/s
Random access Scattered / random reads cannot be fused → effective bandwidth drops far below peak.

Coalescing Strategy

Pattern
  1. Read global memory coalesced into shared memory (whole warp, contiguous)
  2. Then access shared memory randomly at full on-chip bandwidth
  3. (ignoring bank conflicts — covered next)
Modern note Less critical on GPUs with large on-chip caches, but the coalesced global → staged shared pattern is still the workhorse for tiled kernels.

Part J
Bank Conflicts

Shared Memory = Parallel Data Cache (Banks)

bank independent shared-memory port SP streaming processor (CUDA core)

Shared memory is divided into banks (Bank 0 … 31). Each bank serves one address per ~2 cycles. Successive 32-bit words → successive banks.

GenerationBanksSPs concurrent
G80 / GT200168
Fermi+3216
Bank conflict Two threads access the same bank but different addresses → accesses are serialized.

Bank Access Patterns

Bank of address = word_index % 32. For bank = thread*stride % 32:

Stride 1thread i → bank i
No conflict
Random 1:1 permutationeach thread a distinct bank
No conflict
Stride 2banks 0,2,4,… reused
2-way conflict
Stride 8 Many threads collapse onto few banks → heavy conflict (8-way), accesses fully serialized.

Fast & Slow Paths (Fermi+)

Fast Path 1 All threads access different banks → one cycle, full throughput.
Fast Path 2 All threads access the same address → hardware broadcast, no conflict.
Slow Path Multiple threads → same bank, different addresses → accesses serialized.
CostAn N-way conflict takes N times as long as a conflict-free access.

In-Class: Conflict-Free for Which s?

shared-memory access

float f = shared[index + s * threadIdx.x];
sConflict-free?
1Yes ✓
3Yes ✓ (odd, coprime w/ 32 → permutation)
2No ✗ (2-way)
4No ✗ (worse — 4-way)
Rule Odd stride s (coprime with 32) → maps the 32 threads onto a permutation of the 32 banks → conflict-free. Even s shares factors with 32 → conflicts.

SM Resource Partitioning (Occupancy)

SM Dynamically Partitions Its Resources

SM streaming multiprocessor TLP thread-level parallelism

Each SM splits four resources across resident blocks: block slots · thread slots · registers · shared memory.

ResourceG80FermiKepler

G80 Occupancy — Block & Thread Slots

Works
  • 8 blocks × 96 threads = 768 ✓
  • 4 blocks × 192 threads = 768 ✓
Does NOT work
  • 8 blocks × 192 threads = 1536
  • Exceeds the 768 thread-slot limit ✗

The binding limit is whichever resource runs out first — here, thread slots.

G80 Occupancy — Registers & the Cliff

G80 has 8192 registers/SM. Blocks of 256 threads. (Recall the register-spill sketch from Part C — here is the full occupancy picture.)

10 regs / thread
  • \( 8192 / (256 \times 10) = 3.2 \Rightarrow 3 \) blocks
  • 3 × 256 = 768 threads (full!)
11 regs / thread
  • \( 8192 / (256 \times 11) = 2.9 \Rightarrow 2 \) blocks
  • 2 × 256 = 512 threads
Performance cliff One extra register/thread drops occupancy 768 → 512. More registers → less TLP. A small increase in resource use can sharply cut parallelism — unless the extra resources hide global-memory latency.
Part L
Data Prefetching

Hiding Latency with Independent Instructions

Put independent work between a global read and the instruction that uses it. The load runs in the background while the SM keeps issuing.

CUDA C — independent work between load and use

float m  = Md[i];          // global read (long latency)
float f  = a*b + c*d;      // independent — overlaps the load
float f2 = m * f;          // first use of m
Prefetching Issue the load earlier to widen the gap of independent instructions, hiding more of the memory latency.

Tiled Matmul with Prefetch

CUDA C — prefetch the next tile into registers

// load FIRST tile into registers
load Md/Nd tile -> registers (rMd, rNd);

for (/* each tile */) {
    // deposit registers -> shared memory
    Mds[ty][tx] = rMd;  Nds[ty][tx] = rNd;
    __syncthreads();

    // prefetch NEXT tile into registers (overlaps compute)
    load next Md/Nd tile -> registers (rMd, rNd);

    // accumulate dot product from shared memory
    for (k = 0; k < TILE; k++)
        Pvalue += Mds[ty][k] * Nds[k][tx];
    __syncthreads();
}
EffectThe next tile's global loads run while the current tile's multiply-adds execute — latency is hidden behind useful work.
Part M
Instruction Mix & Loop Unrolling

Instruction Mix — The Inner Loop

CUDA C — matmul inner loop

for (int k = 0; k < BLOCK_SIZE; k++)
    Pvalue += Ms[ty][k] * Ns[k][tx];
Per iteration
  • 2 floating-point ops (1 mul, 1 add)
  • 1 loop branch
  • 2 address-arithmetic ops
  • 1 counter increment
Only about 1/3 of issued instructions are the FP work we care about.
SFU bottleneckSpecial-function units: only 4 per SM, 1 instruction/clock each.

Loop Unrolling (BLOCK_SIZE = 16)

CUDA C — fully unrolled inner loop

Pvalue += Ms[ty][0]*Ns[0][tx] + Ms[ty][1]*Ns[1][tx]
        + Ms[ty][2]*Ns[2][tx] + /* ... */
        + Ms[ty][15]*Ns[15][tx];
// or simply:  #pragma unroll BLOCK_SIZE
Wins
  • No loop counter / branch
  • Constant indices → no address arithmetic
  • Nearly all instructions are now FP
Disadvantages
  • Code bloat
  • Higher register pressure
  • Fixed bounds (must know BLOCK_SIZE)
Part N
Thread Granularity

Thread Granularity — How Much Work per Thread?

Compute 1 element of Pd per thread vs. 2 adjacent elements per thread.

Observation Two adjacent Pd elements need the same row of Md. If one thread computes both, that row is loaded once, not twice.
Compute 2 / thread — gains
  • Reduces global-memory access by ~1/4
  • More independent instructions (helps latency hiding)
Costs
  • More registers & shared memory per thread
  • → lower occupancy (ties back to the performance cliff)
BalanceCoarser threads cut redundant traffic but spend resources — tune granularity against occupancy.
