Parallel Deep Learning

Data, model & pipeline parallelism for deep learning
Deep learning is the workload driving today's largest parallel systems. We start with just enough neural-network background (DNNs, SGD, CNNs, Transformers, GNNs), then spend most of our time on how training and inference are parallelized across many devices, and close with model compression — pruning, quantization, and low-rank approximation.

Module 1
Introduction to Neural Networks

Why Now? Three Ingredients

AlgorithmsMost core techniques were invented in the 1980s–90s — backprop, conv nets, recurrent nets.
Big dataWeb-scale labeled datasets arrive in the early 2000s.
HardwareGPUs / accelerators become widely available through the 2010s.
For usOld algorithms + huge data + parallel hardware = a systems problem. The interesting question is how to map this compute onto thousands of devices.

Deep Neural Networks

DNNA collection of simple, trainable mathematical units (neurons) composed into layers that together solve a complicated task.

Each layer applies a linear map then a nonlinearity:

\( h^{(\ell)} = \sigma\!\left( W^{(\ell)} h^{(\ell-1)} + b^{(\ell)} \right) \)

The weights \(W^{(\ell)}\) are the parameters we learn. Modern models have billions of them — which is exactly why they no longer fit on one device.

Training: Gradient Descent

Training minimizes a loss \(L(\theta)\) over parameters \(\theta\). Each step nudges \(\theta\) downhill along the gradient:

\( \theta \leftarrow \theta - \eta \, \nabla_\theta L(\theta) \)

\(\eta\) is the learning rate. The gradient is computed by backpropagation — a backward pass through the layers applying the chain rule.

Two passesForward computes the loss; backward computes \(\nabla_\theta L\). Both are dense tensor algebra — perfect for accelerators.
Each step descends the loss landscape.

Stochastic Gradient Descent (SGD)

Full-batch GD is too costlyComputing \(\nabla L\) over the whole dataset every step is impossibly slow at scale.

SGD estimates the gradient from a small random mini-batch \(B\) of samples each step:

\( \theta \leftarrow \theta - \eta \, \nabla_\theta L_B(\theta) \)
Why it matters for parallelismThe mini-batch is what we split across GPUs in data parallelism — each device processes a slice of \(B\), then the gradients are summed.

Larger batches expose more parallelism but can hurt convergence — the batch size is itself a systems / accuracy trade-off.

CNNs & Convolution

CNNA sequence of convolutional layers interspersed with pooling, normalization, and activations — dominant in vision.

A small filter slides over the input; at each position it computes a weighted sum (a dot product). Weights are shared across positions, so far fewer parameters than a dense layer.

Convolution is the compute hot-spot — usually lowered to dense matrix multiply (im2col + GEMM) on the GPU.

Transformers: Self-Attention

Each token is projected into query, key, value vectors. Attention weights every value by how well its key matches the query:

\( \text{Attn}(Q,K,V) = \text{softmax}\!\left(\tfrac{QK^{\top}}{\sqrt{d_k}}\right) V \)
Multi-headRun h attention computations in parallel on different projections, then concatenate. Heads are an obvious axis to partition across devices.

Graph Neural Networks (GNNs)

GNNNeural networks on relational data — nodes and edges. Each layer aggregates messages from a node's neighbors, then transforms them.

Computation alternates between a sparse aggregate (gather over neighbors) and a dense update (a small MLP per node).

Hard on GPUsThe aggregation is irregular & sparse — poor locality and load imbalance, unlike the dense GEMMs in CNNs/Transformers.

The Rising Compute Demand

Model size and training FLOPs have grown far faster than the memory and throughput of a single accelerator.

Two wallsMemory: parameters + activations + optimizer state exceed one GPU. Time: one device would take months.
ConsequenceLarge-scale training is now fundamentally parallel — the rest of this lecture is how.

Module 1 — Review

1. What single quantity does SGD split across GPUs in data parallelism?

The mini-batch: each device processes a slice of the batch and computes partial gradients, which are then summed across devices.

2. Why are GNNs harder to run efficiently on GPUs than CNNs?

Their neighbor aggregation is sparse and irregular — poor memory locality and load imbalance — whereas CNN/Transformer work is dense GEMM that maps cleanly onto accelerators.
Module 2
Data Parallelism

Three Ways to Decompose

Data parallelismSplit the batch across devices. Each holds a full model replica → independent tasks per device.
Model parallelismSplit the model (neurons / tensors) across devices → independent or dependent tasks.
Pipeline (layer)Split by layers into stages → a chain of dependent tasks.
Big pictureThese are orthogonal axes — real large-scale training combines all three (we get there in Module 5).

Data Parallelism

IdeaReplicate the full model on every device. Each device gets a different shard of the mini-batch, runs forward + backward locally, then they average gradients.
Per-step, per device p

shard = batch[p]                # disjoint slice
loss  = forward(model, shard)
g_p   = backward(loss)          # local gradients
g     = all_reduce(g_p, op=SUM) # sum across devices
model = optimizer.step(model, g)  # identical update

After the all-reduce every replica applies the same averaged gradient, so all replicas stay in sync.

The Memory Issue with Data Parallelism

The catchEvery GPU stores a replica of the entire model — parameters, gradients, and optimizer state.

Data parallelism scales throughput (more samples/sec), but not capacity. If the model doesn't fit on one GPU, replication doesn't help.

ConsequenceCannot train models larger than a single device's memory by data parallelism alone.

This is exactly the gap that model, tensor, and pipeline parallelism fill — they split the model so no one device must hold all of it.

Module 3
Model & Tensor Parallelism

Model Parallelism

IdeaSplit the model into subgraphs and assign each to a different device. Each device holds only part of the parameters.

A simple form divides the neurons within each layer, or assigns whole layers/branches to different devices. Capacity now scales with the number of devices.

CostDevices must exchange activations at every cut in the graph — communication is on the critical path.

Device Placement is Hard

Given a computation graph and a set of heterogeneous devices, which op goes where? The space is combinatorial, and the objective (step time) depends on compute, memory limits, and communication.

A research angleUse ML to optimize placement for ML — e.g. reinforcement learning that learns to assign graph nodes to devices to minimize runtime (Mirhoseini et al.).
Combine the axesIn practice we mix data and model parallelism: replicate some parts across groups while splitting others within a group.

Hand-tuned placement dominates production systems; learned placement is promising but expensive to search.

Tensor Model Parallelism

IdeaPartition the parameters / gradients within a single layer across devices — split the weight matrix itself, not whole layers.

A matmul \(Y = XW\) splits \(W\) by columns: each device computes a slice \(Y_i = X W_i\), then the slices are concatenated (or all-reduced). The whole team cooperates on one layer.

Trade-offFine-grained → frequent collective communication; best kept within a fast interconnect (a single node / NVLink).

Rule of thumbData parallelism when the model fits and you want speed; tensor parallelism when a single layer is too big for one device.

Module 3 — Review

1. What does tensor model parallelism split that ordinary model parallelism does not?

It partitions the weight tensors inside a single layer (e.g. a matmul split by columns), so multiple devices cooperate on one layer — rather than assigning whole layers/subgraphs to devices.

2. Why keep tensor parallelism within a single node?

It requires frequent collective communication of activations every layer; a fast intra-node interconnect (NVLink) keeps that overhead tolerable.
Module 4
Pipeline Parallelism

Pipeline (Layer) Parallelism

IdeaPartition the layers into sequential stages, one per device. Stage i's output feeds stage i+1 — a chain of dependent tasks.

Naively, only one stage is active at a time and the others sit idle. GPipe fixes this by splitting each mini-batch into micro-batches that flow through the pipeline back-to-back.

"GPipe: Efficient Training of Giant Neural Networks using Pipeline Parallelism."

Device Utilization: the Bubble

The bubbleAt pipeline fill and drain, some stages have nothing to do. That idle time is the pipeline bubble — pure overhead.

With m micro-batches and p stages, the bubble fraction is roughly \(\tfrac{p-1}{m+p-1}\). More micro-batches → smaller relative bubble, but more in-flight activations.

1F1B & Interleaved Schedules

Memory problemGPipe runs all forwards, then all backwards — so it must keep activations for every in-flight micro-batch. Memory grows with micro-batch count.
1F1B"One-forward-one-backward": once the pipe is full, each stage alternates a forward and a backward. Backward frees activations early, so peak memory stays bounded.
Interleaved 1F1BGive each device multiple non-contiguous stages (model chunks). This shrinks the bubble further at the cost of more communication.

Same total work, finer-grained schedule → higher utilization. Used in large-model training frameworks (e.g. Megatron / DeepSpeed).

Example: 3D Parallelism in DeepSpeed

DeepSpeed combines all three axes to train models with hundreds of billions of parameters:

TensorWithin a node (NVLink) — finest-grained, most communication.
PipelineAcross nodes — coarse, bandwidth-light boundaries.
DataReplicate the whole 2D grid; all-reduce once per step.

Source: Microsoft Research — "DeepSpeed: Extreme-scale model training for everyone."

Modules 4–5 — Review

1. Why does 1F1B use less memory than GPipe?

It interleaves a backward right after each forward once the pipe is full, so activations are freed early and peak memory stays bounded instead of growing with the micro-batch count.

2. In 3D parallelism, why put tensor parallelism inside a node and pipeline across nodes?

Tensor parallelism communicates every layer and needs the fast intra-node link (NVLink); pipeline only passes activations at stage boundaries, so it tolerates slower inter-node bandwidth.
Module 6
Model Compression

Why Compress?

GoalProduce a simplified model — fewer / smaller parameters, lower inference latency — without significantly diminished accuracy.

Size and speed usually improve together: a smaller model moves less data and does less arithmetic.

Three methodsSparsification (pruning) · Quantization · Low-rank approximation.

Especially important for inference at the edge, where memory, latency, and energy are all constrained.

Pruning (Sparsification)

PremiseNetworks tend to be over-parameterized — many weights contribute little. Remove them to save space, time, and energy.

Today's sparsity methods reach 10–100× reduction in model size with little accuracy loss — and Hoefler et al. argue sparsity could yield up to two orders of magnitude more efficiency.

Accuracy curveLight pruning can reduce noise; a wide middle range stays stable; past a point accuracy drops — and where that point is depends on the network.

What, When & How to Sparsify

WhatModel sparsity (neuron / filter / head — fixed pattern across passes) vs. ephemeral sparsity (activations, gradients — per example).
WhenTrain-then-sparsify (then fine-tune), sparsify-during-training, or fully-sparse training from the start.
HowStatic (prune once, fixed) vs. dynamic (prune & regrow during training).
Structured vs. unstructuredUnstructured removes individual weights → highest compression but irregular. Structured removes whole neurons / filters / heads → less compression but hardware-friendly dense kernels.

Sparse Storage Formats

Once a matrix is sparse, storing every zero is wasteful. Sparse formats store only the m nonzeros plus index metadata.

COOTriples (row, col, value) per nonzero — simple, easy to build, good for construction.
CSRCompressed Sparse Row: values + col_idx + row_ptr. Less index overhead, fast row traversal for SpMV.

Simpler schemes (bitmap, delta) trade index size against random-access cost.

Quantization & Low-Rank

QuantizationStore / compute weights (and activations) in fewer bits — FP32 → FP16 / INT8 / lower.

Smaller data → less memory traffic and faster integer/low-precision arithmetic. Main risk is accuracy loss, mitigated by quantization-aware training.

Low-rank approximationReplace a big weight matrix \(W\) by a product of two thin matrices: \(W \approx U V\) with rank \(r \ll n\).
\( n \times n \;\rightarrow\; n\,r + r\,n \)

Fewer parameters and fewer FLOPs when \(r\) is small — the idea behind low-rank adapters (LoRA).

CombinePruning, quantization, and low-rank are complementary — production models often apply all three.

Module 6 — Review

1. Why is structured pruning often preferred over unstructured despite lower compression?

Removing whole neurons / filters / heads keeps the remaining computation dense and regular, so it maps onto efficient hardware kernels — whereas unstructured sparsity is irregular and hard to accelerate.

2. When would you choose CSR over COO?

CSR has less index overhead and supports fast row traversal (e.g. SpMV); COO is simpler to construct. Build in COO, compute in CSR.

Parallel Deep Learning — Big Picture

DataSplit the batch; all-reduce gradients. Scales throughput, replicates the model.
TensorSplit weights within a layer. Scales layer size; keep it intra-node.
PipelineSplit layers into stages; mind the bubble. 1F1B bounds memory.
3D parallelismCombine all three: \(N = d \times t \times p\), each mapped to the right interconnect level (DeepSpeed).
CompressionPruning + quantization + low-rank shrink the model — size, latency, energy together.
One sentence When a model outgrows one device, partition along data, tensor, and layer axes — matching each to the interconnect — then compress the model to make every device do less.
