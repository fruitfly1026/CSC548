Module 1
Introduction to Neural Networks

Why Now? Three Ingredients

AlgorithmsMost core techniques were invented in the 1980s–90s — backprop, conv nets, recurrent nets.
Big dataWeb-scale labeled datasets arrive in the 2000s.
HardwareGPUs / accelerators become widely available through the 2010s.
For usOld algorithms + huge data + parallel hardware = a systems problem. The interesting question is how to map this compute onto thousands of devices.

Deep Neural Networks

DNNA collection of simple, trainable mathematical units (neurons) composed into layers that together solve a complicated task.

Each layer applies a linear map then a nonlinearity:

\( h^{(\ell)} = \sigma\!\left( W^{(\ell)} h^{(\ell-1)} + b^{(\ell)} \right) \)

The weights \(W^{(\ell)}\) are the parameters we learn. Modern models have billions of them — which is exactly why they no longer fit on one device.

Training: Gradient Descent

Training minimizes a loss \(L(\theta)\) over parameters \(\theta\). Each step nudges \(\theta\) downhill along the gradient:

\( \theta \leftarrow \theta - \eta \, \nabla_\theta L(\theta) \)

\(\eta\) is the learning rate. The gradient is computed by backpropagation — a backward pass through the layers applying the chain rule.

Two passesForward computes the loss; backward computes \(\nabla_\theta L\). Both are dense tensor algebra — perfect for accelerators.
Each step descends the loss landscape.

Stochastic Gradient Descent (SGD)

Full-batch GD is too costlyComputing \(\nabla L\) over the whole dataset every step is impossibly slow at scale.

SGD estimates the gradient from a small random mini-batch \(B\) of samples each step:

\( \theta \leftarrow \theta - \eta \, \nabla_\theta L_B(\theta) \)
Why it matters for parallelismThe mini-batch is what we split across GPUs in data parallelism — each device processes a slice of \(B\), then the gradients are averaged.

Larger batches expose more parallelism but can hurt convergence — the batch size is itself a systems / accuracy trade-off.

CNNs & Convolution

CNNA sequence of convolutional layers interspersed with pooling, normalization, and activations — dominant in vision.

A small filter slides over the input; at each position it computes a weighted sum (a dot product). Weights are shared across positions, so far fewer parameters than a dense layer.

Convolution is the compute hot-spot — usually lowered to dense matrix multiply (im2col + GEMM) on the GPU.

Transformers: Self-Attention

Each token is projected into query, key, value vectors. Attention weights every value by how well its key matches the query:

\( \text{Attn}(Q,K,V) = \text{softmax}\!\left(\tfrac{QK^{\top}}{\sqrt{d_k}}\right) V \)
Multi-headRun h attention computations in parallel on different projections, then concatenate. Heads are an obvious axis to partition across devices.

Graph Neural Networks (GNNs)

GNNNeural networks on relational data — nodes and edges. Each layer aggregates messages from a node's neighbors, then transforms them.

Computation alternates between a sparse aggregate (gather over neighbors) and a dense update (a small MLP per node).

Hard on GPUsThe aggregation is irregular & sparse — poor locality and load imbalance, unlike the dense GEMMs in CNNs/Transformers.

The Rising Compute Demand

Model size and training FLOPs have grown far faster than the memory and throughput of a single accelerator.

Two wallsMemory: parameters + activations + optimizer state exceed one GPU.
Time: one device would take months.
ConsequenceLarge-scale training is now fundamentally parallel — the rest of this lecture is how.
Module 2
Data Parallelism

Three Ways to Decompose

Data parallelismSplit the batch across devices. Each holds a full model replica → independent tasks per device.
Model parallelismSplit the model (neurons / tensors) across devices → independent or dependent tasks.
Pipeline (layer)Split by layers into stages → a chain of dependent tasks.
Big pictureThese are orthogonal axes — real large-scale training combines all three (we get there in Module 5).

Data Parallelism

IdeaReplicate the full model on every device. Each device gets a different shard of the mini-batch, runs forward + backward locally, then average gradients.
Per-step, per device p

shard = batch[p]                # disjoint slice
loss  = forward(model, shard)
g_p   = backward(loss)          # local gradients
g     = all_reduce(g_p, SUM) / P  # average across P devices
model = optimizer.step(model, g)  # identical update

After the all-reduce every replica applies the same averaged gradient, so all replicas stay in sync.

The Memory Issue with Data Parallelism

The catchEvery GPU stores a replica of the entire model — parameters, gradients, and optimizer state.

Data parallelism scales throughput (more samples/sec), but not capacity. If the model doesn't fit on one GPU, replication doesn't help.

ConsequenceCannot train models larger than a single device's memory by data parallelism alone.

This is exactly the gap that model, tensor, and pipeline parallelism fill — they split the model so no one device must hold all of it.

ZeRO & FSDP: Shard the Replica

ZeRO = Zero Redundancy Optimizer (DeepSpeed) FSDP = Fully Sharded Data Parallel (PyTorch) Ψ = number of parameters
Where the memory goesMixed-precision Adam keeps per parameter an FP16 weight and gradient (4 B) plus FP32 master weight, momentum and variance (12 B): 16Ψ bytes on every replica.
ZeRO: partition instead of replicateEach of the \(N\) ranks owns 1/N of the optimizer state (stage 1), of the gradients too (stage 2), of the parameters too (stage 3). Parameters are all-gathered just before a layer runs and freed after; gradients are reduce-scattered to their owner.
CostStages 1–2 move the same bytes as a plain all-reduce, stage 3 about 1.5×. Still data parallelism: each rank sees a different batch, no model code changes.
SchemeMemory / GPU
Plain data parallel\(16\Psi\)
ZeRO-3 / FSDP\(16\Psi/N\)

FSDP is PyTorch's implementation of stage 3; Llama 3 used it as its data-parallel axis.

Rajbhandari et al., "ZeRO," SC 2020; Zhao et al., "PyTorch FSDP," VLDB 2023.
Module 3
Model & Tensor Parallelism

Model Parallelism

IdeaSplit the model into subgraphs and assign each to a different device. Each device holds only part of the parameters.

A simple form divides the neurons within each layer, or assigns whole layers/branches to different devices. Capacity now scales with the number of devices.

CostDevices must exchange activations at every cut in the graph — communication is on the critical path.

Device Placement is Hard

Given a computation graph and a set of heterogeneous devices, which op goes where? The space is combinatorial, and the objective (step time) depends on compute, memory limits, and communication.

A research angleUse ML to optimize placement for ML — e.g. reinforcement learning that learns to assign graph nodes to devices to minimize runtime (Mirhoseini et al.).
Combine the axesIn practice we mix data and model parallelism: replicate some parts across groups while splitting others within a group.

Hand-tuned placement dominates production systems; learned placement is promising but expensive to search.

Tensor Model Parallelism

IdeaPartition the parameters / gradients within a single layer across devices — split the weight matrix itself, not whole layers.

A matmul \(Y = XW\) splits \(W\) by columns: each device computes a slice \(Y_i = X W_i\), then the slices are concatenated (an all-gather). Splitting \(W\) by rows instead gives partial sums that need an all-reduce. The whole team cooperates on one layer.

Trade-offFine-grained → frequent collective communication; best kept within a fast interconnect (a single node / NVLink).

Rule of thumbData parallelism when the model fits and you want speed; tensor parallelism when a single layer is too big for one device.
Module 4
Pipeline Parallelism

Pipeline (Layer) Parallelism

IdeaPartition the layers into sequential stages, one per device. Stage i's output feeds stage i+1 — a chain of dependent tasks.

Naively, only one stage is active at a time and the others sit idle. GPipe fixes this by splitting each mini-batch into micro-batches that flow through the pipeline back-to-back.

"GPipe: Efficient Training of Giant Neural Networks using Pipeline Parallelism."

Device Utilization: the Bubble

The bubbleAt pipeline fill and drain, some stages have nothing to do. That idle time is the pipeline bubble — pure overhead.

With m micro-batches and p stages, the bubble fraction is roughly \(\tfrac{p-1}{m+p-1}\). More micro-batches → smaller relative bubble, but more in-flight activations.

1F1B & Interleaved Schedules

Memory problemGPipe runs all forwards, then all backwards — so it must keep activations for every in-flight micro-batch. Memory grows with micro-batch count.
1F1B"One-forward-one-backward": once the pipe is full, each stage alternates a forward and a backward. Backward frees activations early, so peak memory stays bounded.
Interleaved 1F1BGive each device multiple non-contiguous stages (model chunks). This shrinks the bubble further at the cost of more communication.

Same total work, finer-grained schedule → higher utilization. Used in large-model training frameworks (e.g. Megatron / DeepSpeed).

Beyond 3D: Context & Expert Parallelism (4D / 5D)

Context (sequence) parallelismSplit one sample's sequence across devices. Feed-forward is per-token, but attention needs every key/value, so devices pass K/V blocks around a ring (Ring Attention). Scales context length.
Expert parallelismA mixture-of-experts (MoE) layer routes each token to a few of many experts; put experts on different devices and move tokens with an all-to-all. Scales parameters without more FLOPs per token.

Module 6
LLM Systems: Attention Kernels & Serving

Transformer Anatomy & the Two Phases of Inference

n = sequence length d = model width KV cache = stored keys and values of past tokens
One layerMulti-head attention, then an MLP. Attention: \(O(n^2 d)\) time, \(O(n^2)\) memory per head. The MLP holds about two thirds of the parameters (for \(d_{ff}=4d\)).
PrefillThe prompt's \(n\) tokens run in parallel: big GEMMs, compute-bound. Produces the first token and the KV cache.
DecodeThen one token per step: each step reads all weights and the whole KV cache for ~2 flops per weight. A GEMV in disguise, memory-bound; intensity ≈ sequences batched. The serving problem: keep the GPU busy in decode without exhausting KV memory.
Vaswani et al., NeurIPS 2017; Pope et al., "Efficiently Scaling Transformer Inference," MLSys 2023.

FlashAttention: Tiling the Attention Kernel

Standard attentionWrite \(S = QK^{\top}\) (\(n \times n\)) to HBM, read it for softmax, write \(P\), read it for \(PV\). \(O(n^2)\) traffic: memory-bound, and the \(n \times n\) matrix limits sequence length.
FlashAttentionLoad tiles of Q, K, V into SRAM; keep a running softmax (row max and sum, rescaled as blocks arrive) and accumulate the output tile. The \(n \times n\) matrix is never written; backward recomputes it from saved statistics.
ResultExact attention, memory linear in \(n\), up to 3× faster than the standard kernel (original paper); FlashAttention-2 adds about 2× by re-partitioning work across warps.
Dao et al., "FlashAttention," NeurIPS 2022; Dao, "FlashAttention-2," ICLR 2024.

KV Cache & PagedAttention (vLLM)

The KV cache is bigEvery token adds its K and V for every layer: about 800 KB per token for a 13B FP16 model, 1.6 GB for a 2K-token sequence. The cache, not the weights, decides how many requests fit.
The wasteEarlier systems reserved one contiguous buffer per request at its maximum length; fragmentation and over-reservation wasted 60–80% of KV memory.
PagedAttentionStore the cache in fixed-size blocks (e.g. 16 tokens); a per-request block table maps logical to physical blocks, like virtual-memory paging. Blocks are allocated on demand and shared across requests with copy-on-write.

Result: near-zero waste, 2–4× serving throughput at the same latency vs. FasterTransformer and Orca (paper's figures).

Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention," SOSP 2023.

Scheduling Requests: Batching, Chunking, Disaggregation

TTFT = time to first token (prefill latency) TPOT = time per output token (decode latency)
Continuous batching (Orca)Static batching waits for the whole batch to finish; short requests leave GPUs idle. Orca schedules at the iteration level: after every decode step, finished sequences leave and new ones join. Batch the GEMMs, run attention per request.
Chunked prefill (Sarathi-Serve)A long prompt's prefill stalls every decode in the batch. Split the prefill into chunks and run each chunk together with the pending decode steps: decodes never stall, and the chunk fills the GPU the decodes left idle.
Disaggregation (DistServe)Prefill is compute-bound, decode is memory-bound; on shared GPUs they interfere. Run them on separate GPU pools, each with its own parallelism, and ship the KV cache across. TTFT and TPOT are tuned independently.
The common threadServing is a scheduling problem: the goal is a full GPU at every decode step under latency targets, which is the utilization story of this course with requests instead of threads.
Yu et al., "Orca," OSDI 2022; Agrawal et al., "Sarathi-Serve," OSDI 2024; Zhong et al., "DistServe," OSDI 2024.

Faster Decoding: Speculation, Prefix Sharing, MoE

Speculative decodingA small draft model proposes \(k\) tokens; the large model verifies all \(k\) in one parallel forward pass and keeps the longest accepted prefix. With rejection sampling the output distribution is unchanged. 2–3× faster decoding (paper's figure): spends spare compute to cut memory-bound steps.
Prefix sharing (SGLang)System prompts, few-shot examples and chat history repeat across requests. RadixAttention keeps KV blocks of shared prefixes in a radix tree and reuses them, skipping their prefill. Up to 6.4× higher throughput on such workloads (paper's figure).
MoE inferenceEach token touches only a few experts, so FLOPs per token stay small while parameters grow. Experts are spread over GPUs with expert parallelism; the cost is a token all-to-all per MoE layer and load imbalance when a few experts are popular.
PatternEvery trick trades a resource the decode step has spare (compute, memory for reused prefixes, more GPUs) for the one it lacks (bytes per step).
Leviathan et al., "Fast Inference from Transformers via Speculative Decoding," ICML 2023; Zheng et al., "SGLang," NeurIPS 2024; Lepikhin et al., "GShard," ICLR 2021.
Module 7
Model Compression

Why Compress?

GoalProduce a simplified model — fewer / smaller parameters, lower inference latency — without significantly diminished accuracy.

Size and speed usually improve together: a smaller model moves less data and does less arithmetic.

Three methodsSparsification (pruning), Quantization, Low-rank approximation.

Especially important for inference at the edge, where memory, latency, and energy are all constrained.

Pruning (Sparsification)

PremiseNetworks tend to be over-parameterized — many weights contribute little. Remove them to save space, time, and energy.

Today's sparsity methods reach a 10–100× (up to ~two-orders-of-magnitude) reduction in model size with little accuracy loss.

Hoefler et al., "Sparsity in Deep Learning," JMLR 22, 2021.
Accuracy curveLight pruning can even improve accuracy (it acts as a regularizer); a wide middle range stays stable; past a point accuracy drops — and where that point is depends on the network.

What, When & How to Sparsify

WhatModel sparsity (neuron / filter / head — fixed pattern across passes) vs. ephemeral sparsity (activations, gradients — per example).
WhenTrain-then-sparsify (then fine-tune), sparsify-during-training, or fully-sparse training from the start.
HowStatic (prune once, fixed) vs. dynamic (prune & regrow during training).
Structured vs. unstructuredUnstructured removes individual weights → highest compression but irregular. Structured removes whole neurons / filters / heads → less compression but hardware-friendly dense kernels.

Sparse Storage Formats

Once a matrix is sparse, storing every zero is wasteful. Sparse formats store only the m nonzeros plus index metadata.

COOTriples (row, col, value) per nonzero — simple, easy to build, good for construction.
CSRCompressed Sparse Row: values + col_idx + row_ptr. Less index overhead, fast row traversal for SpMV.

Simpler schemes (bitmap, delta) trade index size against random-access cost.

Quantization

PTQ = post-training quantization QAT = quantization-aware training
IdeaStore and compute weights (and activations) in fewer bits: FP32 → FP16/BF16 → INT8 → 4-bit, via a scale and zero point, \(x \approx s\,(q - z)\).
Why it paysFewer bytes per weight means less memory traffic, which bounds inference; matrix engines also run faster at low precision.
Risk and remediesAccuracy loss, mostly from outliers that stretch the scale. Remedies: per-channel or per-group scales; keep outliers in higher precision; QAT trains with rounding in the loop.

Weight-only quantization is the common choice for LLM inference: weights dominate memory traffic, activations stay in 16-bit.

Jacob et al., CVPR 2018 (integer-arithmetic inference); Dettmers et al., LLM.int8(), NeurIPS 2022; Frantar et al., GPTQ, ICLR 2023.

Low-Rank Approximation

IdeaReplace a big weight matrix \(W\) by a product of two thin matrices, \(W \approx U V\), with rank \(r \ll n\). Storage and FLOPs drop from \(n^2\) to \(2nr\).
\( n \times n \;\rightarrow\; n\,r + r\,n \)
How to get itTruncated SVD of a trained weight, or train the layer in factored form. Works when singular values decay fast.
LoRA: low-rank for fine-tuningFreeze \(W\); train a low-rank update \(\Delta W = BA\) with \(r\) of 8 to 64. Far fewer trainable parameters, and \(BA\) merges into \(W\) after training: no inference cost.

Same idea as the CP and Tucker decompositions in the Linear Algebra lecture: a low-rank factorization is compression.

Denton et al., NeurIPS 2014 (low-rank expansions of conv nets); Hu et al., "LoRA: Low-Rank Adaptation of Large Language Models," ICLR 2022.

Parallel Deep Learning — Big Picture

DataSplit the batch; all-reduce gradients. Scales throughput, replicates the model.
TensorSplit weights within a layer. Scales layer size; keep it intra-node.
PipelineSplit layers into stages; mind the bubble. 1F1B bounds memory.
3D parallelism and beyondCombine all three: \(N = d \times t \times p\), each mapped to the right interconnect level (DeepSpeed). Context and expert axes extend it to 4D/5D.
LLM servingDecode is memory-bound: tile attention, page the KV cache, batch continuously, speculate.
CompressionPruning + quantization + low-rank shrink the model — size, latency, energy together.
One sentence When a model outgrows one device, partition along data, tensor, and layer axes — matching each to the interconnect — then compress the model to make every device do less.
