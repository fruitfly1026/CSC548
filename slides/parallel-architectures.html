Lecture 1 · 09/30
Cache Coherence

Will This Parallel Code Work?

Parallel reduction with a lock

sum = 0;
begin parallel
  for (i = 0; i < 2; i++) {
    lock(id, myLock);
    sum = sum + a[i];
    unlock(id, myLock);
  }
end parallel
Print sum;

Suppose a[0] = 3 and a[1] = 7. Will it print sum = 10?

Not necessarilyWith write-back caches, each core can hold its own private copy of sum. The lock gives mutual exclusion, but it does not by itself make the caches agree.

Making the caches agree is the hardware's job — the cache coherence protocol.

The Coherence Problem

The problemThe same line can sit in several private caches. After one core writes it, a read elsewhere can return a value older than the latest write.
Two requirements Write propagation — a write reaches the other copies, by invalidating or updating them.
Write serialization — all cores see writes to one location in the same order.

Why Write Serialization Matters

P1 and P2 both write x. If P3 and P4 receive the two writes in different orders, they settle on different final values of x.

ResultThe system is incoherent — two cores disagree forever about one variable.
How a bus fixes itEvery write must win the bus, and every cache watches the bus. The bus order becomes the single global order of writes.

Bus-Based SMP & Snooping

A snooper at every cache and at the memory controller.

A symmetric multiprocessor (SMP): private caches, one shared memory, and a bus — the simplest interconnect.

  • A snooper at each cache watches every bus transaction
  • If a transaction touches a line it holds, it changes that line's state
  • The memory controller snoops too, deciding whether memory or a cache supplies the data
In shortCoherence = snoopers + an extended per-line state machine on top of the ordinary cache.

Write-Through Coherence — and Why We Move On

The simplest protocol: write-through, write-invalidate. Each line is only Valid or Invalid.

Events: PrRd, PrWr from the core; BusRd, BusWr snooped from the bus. Every write goes on the bus, so it invalidates every other copy.

The problemEvery write uses the bus — even repeated writes to one line by one core. The bus saturates quickly as cores are added.
The fixUse write-back caches: write hits stay in the cache, and the bus is used only when sharing requires it. That is MSI.
Write-through, write-invalidate: only Valid / Invalid.

MSI: A Write-Back Invalidation Protocol

Three states

  • Modified (M) — the only copy, dirty
  • Shared (S) — one or more copies, memory up to date
  • Invalid (I) — not present, or invalidated

Processor events

PrRd (read), PrWr (write)

Bus transactions

  • BusRd — get a copy, no intent to modify
  • BusRdX — get a copy with intent to modify
  • BusUpgr — already have the data; just invalidate the others
  • Flush — put the dirty line on the bus
Two key verbsInvalidation: any state → I. Intervention: M → S, when a peer's read forces the owner to supply the data.

MSI — Processor-Initiated Transitions

Label = event / bus action.
  • I → S on PrRd: issue BusRd
  • I → M on PrWr: issue BusRdX
  • S → M on PrWr: issue BusRdX (or the cheaper BusUpgr)
  • S read hits and M read/write hits need no bus
MSI's weaknessA read-then-write to a line no one else shares still costs two bus transactions: BusRd, then BusRdX or BusUpgr. MESI fixes this.

MSI — Bus-Initiated (Snooped) Transitions

Snooped transactions; M supplies data via Flush.
  • M → S on snooped BusRd: Flush (intervention — a peer wants to read)
  • M → I on snooped BusRdX: Flush and give up the line
  • S → I on snooped BusRdX: invalidate
  • S stays S on snooped BusRd
Memory's roleWhen a cache Flushes, the memory controller cancels its own read — the dirty owner supplies the freshest data, and memory is updated too.

MESI — Adding the Exclusive State

MSI's flawA sequential program pays two bus transactions per read-then-write, even though no one else shares the line.

Add a fourth state:

  • Modified — dirty, sole copy
  • Exclusive — the only copy, and clean (matches memory)
  • Shared — two or more caches may hold it
  • Invalid
I → E or I → S?On a read miss, other caches answer a wired-OR bus signal C ("copy exists"). No copy → enter E; otherwise enter S.
The payoffE → M on a write is silent — no bus transaction. A read-then-write to a private line now costs one transaction, not two.
Flush vs. FlushOptA snooped M line must Flush. E and S lines may optionally supply data (FlushOpt), betting a peer cache beats memory.
Illinois MESI: M. Papamarcos & J. Patel, ISCA 1984.

MESI — Processor-Initiated Transitions

  • I → E on PrRd when C is not asserted
  • I → S on PrRd when C is asserted
  • E → M on PrWr: silent
  • S → M on PrWr: BusUpgr
  • I → M on PrWr: BusRdX

Snooped side, same idea as MSI: a peer's BusRd downgrades M/E → S; a peer's BusRdX or BusUpgr invalidates M/E/S → I.

MOESI — Allowing Dirty Sharing

MESI's flawA shared line must be clean. So whenever a peer reads a dirty line, MESI writes it back to memory — lots of memory traffic.
MOESI's fixLet a dirty line be shared. One cache holds it in the Owned (O) state: it supplies the data on snooped reads and owes the eventual write-back.
  • M → O on a snooped BusRd: supply the data, stay dirty, memory not updated
  • An S copy of a dirty line can be dropped silently
  • The O copy must be written back when evicted

Used in AMD processors (e.g. Opteron).

Dragon — Update Instead of Invalidate

Four states, and no Invalid (a line is either present and valid, or absent):

  • E — exclusive, clean
  • Sc — shared-clean; I'm not the owner
  • Sm — shared-modified; I'm the owner (at most one cache)
  • M — modified, sole copy
New bus transactionBusUpd broadcasts the single word written, and every sharer updates its copy in place.
Key differenceA write updates peers instead of invalidating them. Peers keep valid copies, so their next reads still hit — no coherence misses.
The costEvery write to a shared line puts a BusUpd on the bus, even if the peers never read that line again. And the extra live lines raise conflict and capacity misses.
On evictionSc can be dropped silently; Sm must Flush, because it is the owner.

Coherence Misses: True vs. False Sharing

Coherence missA miss on a line that was invalidated because another core wrote it. It happens only in invalidation protocols.
True sharingThreads really share the same data item. Inherent to the algorithm.
False sharingThreads touch different items that happen to sit in the same cache line. An artifact of line granularity — fix it with padding or a per-thread layout (Topic 6).
Larger…True-sharing missesFalse-sharing misses
cache sizeincreaseincrease

A bigger cache keeps more shared lines resident, so fewer sharing misses are hidden by eviction. A bigger line brings more useful data per true-sharing miss, but packs more unrelated items together — more false sharing.

Coherence in a Real Cache Hierarchy

Multi-level caches

  • Downstream: an L1 write must reach the coherent L2 — through a write-through L1, or a write notification from a write-back L1
  • Upstream: an invalidation at L2 must be passed up to L1 if L1 may hold the line
  • Inclusion helps: if the line is not in L2, it cannot be in L1, so there's no need to disturb L1

Prefetching

  • A prefetch of a dirty line forces the owner to downgrade
  • The prefetched line may be invalidated before it is used
  • The owner's next write is delayed — it must re-invalidate first
Timeliness matters moreA mistimed prefetch in a multiprocessor can hurt both the prefetching cache and the cache that supplied the line.

Beyond the Bus: Directory-Based Coherence

Why snooping stops scaling Long shared wires force a low clock, and arbitration slows as clients are added. Every request is broadcast to every cache, so bandwidth saturates and contention is everywhere.
The ideaReplace broadcast with a directory. Each block has a home node that records which caches hold it, so requests go point-to-point only to the caches involved.

Per block, the directory keeps the sharers (e.g. a bit-vector, one bit per cache) and a state:

Dir stateMeaning
EMone owner holds it Exclusive or Modified
Sone or more caches hold it Shared
Uuncached

The caches still run MESI. The directory merges E and M, because the E → M transition is silent and sends no message.

One sentenceEvery protocol enforces write propagation and write serialization. They differ in how many states they track and whether a write invalidates or updates the peers — trading bus traffic against miss rate.
For your codeCoherence works on whole cache lines. Writes to lines that other cores hold cost invalidations, and false sharing pays that cost for data that isn't even shared.
Lecture 2 · 10/05
Memory Consistency

Cache Coherence vs. Memory Consistency

Cache coherence Orders the writes to a single memory location.
Needed only in systems with caches. (Lecture 1.)
Memory consistency Orders reads and writes across all memory locations.
Matters in systems with or without caches.
Why we need a consistency model Per-location coherence is not enough. A program's correctness can depend on how a write to A is ordered relative to a write to B. The consistency model is the contract that says which orderings across locations the hardware guarantees.
The question for this lectureA core finishes loads and stores out of order for speed. How much of that reordering may a program observe — and how do we rein it in when we need to?

Programmer's Intuition I — Program Order

Post–wait handoff (init datum = datumIsReady = 0)

// P0                  // P1
S1: datum = 5;         S3: while (!datumIsReady) ;
S2: datumIsReady = 1;  S4: ... = datum;   // expect 5

We expect S4 to read 5. That breaks if S2 becomes visible before S1, or if S4 runs before S3.

Expectation 1 · Program order A thread's memory accesses happen in the order they appear in the source code.
The subtle part That order must hold not just within the thread, but as seen by every other thread.

Programmer's Intuition II — Atomicity

Three threads (init x = y = z = xReady = xyReady = 0)

// P0            // P1                   // P2
S1: x = 5;       S3: while (!xReady) ;   S6: while (!xyReady) ;
S2: xReady = 1;  S4: y = x + 4;          S7: z = x * y;
                 S5: xyReady = 1;

We expect z = 45: if the new x reached P1, it must also have reached P2.

Expectation 2 · AtomicityA write appears to happen instantaneously with respect to all processors.

How it breaks when a write is not atomic:

StepWhat happens
1New x and xReady reach P1, not yet P2
2P1 computes y; y and xyReady reach P2 before x does
3P2 reads the old x = 0, so z = 0, not 45

Sequential Consistency (SC)

Both expectations together Each processor's accesses are performed in program order, and each access is performed atomically.
"A multiprocessor is sequentially consistent if the result of any execution is the same as if the operations of all processors were executed in some sequential order, and the operations of each individual processor appear in this sequence in the order specified by its program."
— Leslie Lamport, 1979

Programmers' expectations match SC very closely — it is the model people reason with by default.

SC Outcomes — Example A

init a = b = 0

// P0        // P1
S1: a = 1;   S3: ... = b;
S2: b = 1;   S4: ... = a;

No synchronization, so several outcomes are legal. Under SC, S1 → S2 and S3 → S4 always hold.

Interleaving(a, b) read by P1
S1 S2 S3 S41, 1
S3 S4 S1 S20, 0
S1 S3 S2 S41, 0
any SC order0, 1 is impossible

(a, b) = (0, 1) needs S4 before S1 (to read a = 0) and S2 before S3 (to read b = 1). With program order that is a cycle.

On a non-SC machine(0, 1) appears if the two writes (S1, S2) or the two reads (S3, S4) get reordered. A forbidden outcome is the fingerprint of a reordering.

SC Outcomes — Example B: the Store-Buffer Test

init a = b = 0

// P0          // P1
S1: a = 1;     S3: b = 1;
S2: ... = b;   S4: ... = a;

Each thread writes one flag, then reads the other's.

Interleaving(b read by P0, a read by P1)
S1 S2 S3 S40, 1
S3 S4 S1 S21, 0
S1 S3 S2 S41, 1
any SC order0, 0 is impossible
But real machines produce (0, 0)On x86 and ARM, each core parks its store in a store buffer and reads the other flag's old value. The store → load order is broken — exactly the order the next relaxed model gives up.
x86-TSO and the (0,0) outcome: Sewell et al., "x86-TSO: A Rigorous and Usable Programmer's Model for x86 Multiprocessors," CACM 2010.

Building an SC Machine — and What It Costs

What SC requires

  • The compiler must not reorder memory accesses (e.g. volatile on critical variables)
  • The core exposes accesses to the cache one at a time, in program order
  • A load completes when it reads the cache; a store completes when its invalidation is posted on the bus
The costIf ld A misses and ld B would hit, B still waits for A. Strict SC throws away the latency hiding that out-of-order cores are built for.

Making SC faster

PrefetchingKeep the order, but fetch lines early — shared for loads, exclusive for stores — so each access hits.
Load speculationLet a younger load read the cache early, marked speculative. If its line is invalidated before it retires, cancel and re-execute it.

Only loads are speculated: a store, once exposed, cannot be taken back.

Relaxed Consistency Models & Fences

Idea: let some accesses reorder or overlap for speed. Because that can break intuition, give the programmer a safety net to use where order matters.

Memory fenceA fence orders every load/store before it ahead of every load/store after it. Inserting fences is the programmer's — or the library writer's — job.

The family, from least to most relaxed: PC (processor consistency), WO (weak ordering), RC (release consistency).

How a fence works
  • Wait until all older writes are posted on the bus (or acknowledged)
  • Wait until all older reads have completed
  • Flush the pipeline so younger accesses can't issue early
If you roll your own synchronizationWithout fences, a relaxed machine does not guarantee your flag or lock works. Thread libraries already contain the right fences.

The Four Orderings — What Each Model Keeps

Every access pair is one of four kinds. A consistency model is defined by which of them it preserves between ordinary accesses.

SCkeptkeptkeptkeptevery access
PCkeptkeptrelaxedkeptevery access except ST→LD
WOrelaxedrelaxedrelaxedrelaxedsynchronization points (full fence)

The tensionEach step down the table allows more overlap and more speed, and moves more of the ordering job to the programmer.

x86 also relaxes only store → load, like PC. POWER and ARM are much weaker and rely on fences and acquire/release.

Processor Consistency (PC)

PC drops one orderStore → load. A load may complete before an older store to a different address.
  • Committed stores wait in a write buffer and reach the cache later
  • Loads don't wait for older stores, so they hit the cache right away — no speculation needed
  • A load to the same address as a buffered store reads it straight from the buffer
  • PC also gives up write atomicity
Post–wait still works under PC 

// P1               // P2
data = 2000;        while (flag == 0) ;
flag = 1;           print(data);
Where PC differs from SC 

// P1                  // P2
flag1 = 1;             flag2 = 1;
if (flag2 == 0) ...    if (flag1 == 0) ...
Both stores are buffered and both loads bypass them, so both ifs can fire — the store-buffer test again.

Weak Ordering (WO)

Reorder freely inside each block; order at every synch.
Key observationIf you needed one access ordered after another, you would have synchronized them. Most correct programs are properly synchronized.
Key ideaReorder or overlap every access, except around synchronization. Before a synch, all earlier accesses finish; after it, no access starts until the synch finishes.
The catchThe hardware must know which accesses are synchronization. Atomic instructions and LL/SC count automatically. A plain load/store used as a flag must get a fence, or be turned into an atomic.

Release Consistency (RC): Acquire & Release

RC splits synchronization into two kinds, because they need ordering in opposite directions.

Acquire — e.g. lock, wait()No access after the acquire may run until the acquire completes. It blocks upward migration, so nothing in the critical section runs before the lock is held.
Release — e.g. unlock, post()Every access before the release must be performed first. It blocks downward migration, so the critical section's writes are visible before the lock is freed.
Why it beats WOA full fence blocks both directions; acquire and release each block only one. Accesses outside a critical section may move into it, so more work overlaps.

RC in Practice: Post–Wait and Locks

Post–wait

// P0                           // P1
S1: datum = 5;                  S3: while (!datumIsReady) ; // acquire
S2: datumIsReady = 1; // release S4: ... = datum;

S2 is a release, so S1 is performed before it. S3 is an acquire, so S4 cannot read datum early. P1 is guaranteed to read 5.

Lock-protected update

// producer             // consumer
lock(L1);   // acquire  lock(L1);   // acquire
sum += x;               ... = sum;
unlock(L1); // release  unlock(L1); // release

The update to sum is performed before unlock; the consumer's lock completes before it reads sum.

Lazy release consistencyNew values aren't needed until someone acquires. LRC sends them in one batch at the acquire instead of at each write — a win when many small messages are expensive, as in software shared memory.

Fences in Real ISAs

PowerPC — separate fence instructions

; P0 (post)          ; P1 (wait)
st  datum, 5         loop: ld r, ready
lwsync               cmp r, 0 ; beq loop
st  ready, 1         isync
                     ld  ..., datum

lwsync on the post side keeps datum ahead of ready; isync on the wait side acts as an acquire fence, so datum isn't read too soon.

IA-64 — labeled accesses

; P0 (post)            ; P1 (wait)
st       datum, 5      loop: ld.acq r, ready
st.rel   ready, 1            cmp r, 0 ; beq loop
                             ld  ..., datum

With per-access labels, the release store (st.rel) and acquire load (ld.acq) are enough — no separate fence instruction. This is RC built into the ISA.

PowerPC sequence: IBM Power ISA / PowerPC Architecture Book.

What You Actually Write: Language-Level Models

Java, C, and C++ (since 2011) define the memory model themselves. You mark the synchronizing accesses; the compiler emits the fences the hardware needs.

C++11 — post–wait with acquire/release

std::atomic<int> ready{0};
int datum;

// producer
datum = 5;
ready.store(1, std::memory_order_release);

// consumer
while (ready.load(std::memory_order_acquire) == 0) ;
use(datum);   // guaranteed to see 5
The rulesAtomics default to memory_order_seq_cst (SC). A data race on a plain variable is undefined behavior — so the post–wait flag must be an atomic, not a plain int.
OpenMP (Topic 4)#pragma omp flush is OpenMP's fence. Since OpenMP 5.0, atomic and flush take memory-order clauses such as seq_cst, acquire, and release.
Java Memory Model: Manson, Pugh & Adve, POPL 2005. C++11: ISO/IEC 14882:2011. OpenMP 5.0 specification, 2018.

Big Picture

CoherenceOrders writes to one location. Snooping protocols (MSI, MESI, MOESI, Dragon) on a bus; directories beyond it.
ConsistencyOrders accesses across locations. SC matches intuition; PC, WO, and RC relax it for speed.
Your side of the contractSynchronize with locks, atomics, or acquire/release. Don't build flags out of plain variables.
One sentenceHardware keeps each cache line coherent, but it only keeps your accesses in order at the synchronization points you mark.

The four orderings — LD→LD, LD→ST, ST→LD, ST→ST — and which ones a model keeps are the whole story of consistency.
