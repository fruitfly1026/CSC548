The Parallel Machine Map
Module 1
Classifying Parallel Machines

Why We Need a Taxonomy

No single standardUnlike the one von Neumann model for serial machines, there is no single standard for parallel machines — dozens of architectures have been built and are in use.

The modern trend: fewer fully custom designs, more commodity CPUs & GPUs wired together with specialized interconnects. A taxonomy lets us reason about a machine we've never seen.

Two lenses we'll useEvery machine can be placed along two independent axes:
• Flynn's taxonomy — by instruction & data streams (this module).
• Memory model — shared vs. distributed, UMA / NUMA (Module 2).

A given machine is usually a point in both spaces at once, e.g. "a MIMD, distributed-memory, CC-NUMA-per-node cluster."

Emphasize that the two lenses are orthogonal. Students often conflate "SIMD" with "shared memory" — they are unrelated classifications. A GPU is SIMD-ish (SIMT) but has its own distributed device memory; a multi-socket Xeon is MIMD with shared NUMA memory.

Classify a machine by how many instruction streams and data streams it runs at once (Flynn, 1966).

SIMD intuition"Everyone flip a coin; if heads, raise your hand." One order, executed by all on their own datum.
MIMD intuitionEach processor runs its own program on its own data, on its own schedule.
Where the course livesMost machines you'll program are MIMD; GPUs add SIMD lanes underneath.
The taxonomy is coarse — that's the point and the criticism. It captures the control model, not the memory model. Two SIMD lanes vs. two full MIMD cores differ mainly in whether they fetch one shared instruction or two independent instruction streams.

Flynn's Four Classes in Detail

SISDSingle Instruction, Single Data. One instruction stream on one data stream — a classic single-core CPU. No parallelism (though pipelining & superscalar hide inside it).
SIMDSingle Instruction, Multiple Data. One instruction applied to many data elements in lockstep — vector units (AVX) and GPU warps. The engine of data parallelism.
MISDMultiple Instruction, Single Data. Many instruction streams on one data stream — rare; occasionally cited for systolic arrays or fault-tolerant pipelines (same datum checked several ways).
MIMDMultiple Instruction, Multiple Data. Independent processors, each with its own program & data — multicore CPUs & clusters. The general parallel machine; in practice usually run as SPMD.
Real machines mix themA MIMD cluster of multicore nodes, each core with SIMD vector units, each node with a SIMT GPU. You'll write mostly MIMD (MPI / OpenMP) with SIMD & GPU underneath.

SIMT is a variant of SIMDNVIDIA's SIMT (Single Instruction, Multiple Thread) is SIMD with per-lane masking: a warp of 32 threads shares one instruction, but threads may diverge on branches (at a cost). Detail in Topic 8 (GPU).
MISD is the empty box everyone argues about. The honest answer: no commercially important machine is purely MISD; it survives mostly as a teaching category and in safety-critical lockstep designs (e.g., automotive/aerospace cores running the same data through redundant pipelines to catch faults).

SIMD & MIMD, Up Close

SIMD — one controller, many lanes A single control unit broadcasts each instruction to many ALUs that run it in lockstep on different data.
  • Vector processors (Cray) and CPU SIMD units (SSE / AVX / AVX-512)
  • Array processors (historic: CM-1, MasPar)
  • GPUs — SIMT: a warp of 32 threads shares one instruction
  • Great for regular, data-parallel work; hurt by branch divergence
MIMD — independent processors Each processor has its own control & data — the general parallel machine. Split by memory:
  • Multiprocessors — shared memory (SMP, NUMA) → program with OpenMP
  • Multicomputers — distributed memory / clusters → program with MPI
  • Styles: SPMD (one program, many data) and MPMD

SPMD vs. MPMD — How We Actually Use MIMD

SPMDSingle Program, Multiple Data. Every process runs the same executable; behavior differs by rank / thread id. This is how almost all MPI and OpenMP code is written.

int rank; MPI_Comm_rank(MPI_COMM_WORLD, &rank);
if (rank == 0) collect_results();   // same binary,
else           compute_chunk(rank); // branch by id

SPMD is a programming style, not a hardware class — it runs on MIMD hardware.

MPMDMultiple Program, Multiple Data. Different executables cooperate — e.g. a coupled ocean + atmosphere climate model, or a master/worker with distinct binaries. MPI supports it via MPMD launch (mpirun -np 2 ocean : -np 6 atmos).
Rule of thumbReach for SPMD by default (one code path, easier to maintain); use MPMD only when the tasks are genuinely different programs.
Key distinction to nail: Flynn's MIMD describes the hardware's capability (independent instruction streams); SPMD/MPMD describe how the programmer organizes the software on top of it. A single MPI program launched on 1000 ranks is SPMD running on MIMD hardware — the most common HPC pattern by far.
Module 2
Coupling & Memory Organization

Tightly- vs. Loosely-Coupled

Tightly coupledProcessors share one physical memory and communicate through it at hardware speed (ns). One OS image. → multiprocessors (SMP, NUMA).

Communication is implicit: write a variable, another core reads it. Fast, but the shared memory limits how many processors you can add.

Loosely coupledEach node has its own memory & OS; they communicate by messages over a network (µs). → multicomputers / clusters.

Communication is explicit: you must send & receive. Slower per message, but scales to millions of cores.

The tradeTighter coupling = easier programming, harder scaling. Looser coupling = harder programming, near-unlimited scaling. Real machines are loosely-coupled clusters of tightly-coupled nodes.

Shared vs. Distributed Memory

Shared memory (one address space)
Communicate by reading/writing shared variables → OpenMP.
Distributed memory (private per node)
Communicate by messages over the network → MPI.
The programming model follows the memory modelShared address space → think in threads & locks. Separate address spaces → think in send/receive. Getting this mapping right is half of parallel programming.

Shared Memory: Bus-Based SMP

Bus-based SMPAny processor can read/write any memory location over a shared bus — one global address space, uniform access.

Advantage: cheap connection; threads communicate just by touching shared variables.

Limit: the bus bandwidth — it doesn't scale past a modest number of processors, and two PEs modifying the same data need locks.

One bus, one memory pool — the classic UMA machine.
The single bus is the scaling wall for UMA. Every core snoops it; add cores and contention rises. This is exactly why real many-core and multi-socket systems moved to distributed (NUMA) memory with a point-to-point interconnect instead of one shared bus.

Memory Organization: UMA, NUMA, CC-NUMA

UMA Uniform Memory Access NUMA Non-Uniform Memory Access CC-NUMA Cache-Coherent NUMA

Two axes: address space (shared vs. message-passing) and physical memory (centralized vs. distributed). NUMA / CC-NUMA are distributed shared memory.

AxisUMANUMA / CC-NUMAMessage-passing cluster
Address spacesharedsharedseparate (private)
Physical memorycentralizeddistributeddistributed
UMACentralized shared memory — one pool over a shared bus; uniform latency but doesn't scale.
NUMADistributed shared memory — memory across nodes (local fast, remote slower); one address space; scales.
CC-NUMANUMA + hardware cache coherence — most multi-socket servers today.
The new problem: coherenceThe same variable cached in two PEs may hold different values — the cache controller must enforce coherence. CC-NUMA solves it in hardware. (Lecture 2.)
NUMA: each PE owns local memory; all reachable, remote is slower.
Fragment order tells the story: UMA first, then distribute the memory to get NUMA (scales), then note that distributed caches break the single-value illusion (coherence problem), and finally CC-NUMA fixes it in hardware. Every modern 2- or 4-socket server is CC-NUMA. We open Lecture 2 on exactly that coherence problem; the programmer-facing consequence (first-touch page placement) is in Topic 6.
Module 3
Inside a Node — Multicore, SMP & Clusters

Multicore & the Chip Multiprocessor

Why multicore?Frequency scaling hit a power wall (~2005). Instead of one faster core, put several cores on one die — a chip multiprocessor (CMP). Performance now comes from parallelism, not clock speed.
SMPSymmetric Multiprocessing — identical cores, equal access to shared memory, one OS scheduling across all of them. A multicore chip is an SMP on a die.

"Symmetric" = no master/worker asymmetry; any core can run any task.

Private L1/L2 per core, shared L3 per socket.
Tie back to the power wall from Topic 1 (the "free lunch is over"). The CMP is the industry's answer: the transistor budget still grows, but it buys cores, not gigahertz. That is precisely why this course exists — the speedup is now the programmer's responsibility.

Cache Hierarchy per Socket

Within a socket the cores share a memory hierarchy. Levels get larger and slower as you descend; the top levels are private, the last level is shared.

LevelScopeRough latency
L1 (I & D)per-core, private~4 cyc
L2per-core (usually)~10–15 cyc
L3 (LLC)shared per socket~40 cyc
Local DRAMthis NUMA node~200+ cyc
Remote DRAMother socket1.5–2× local
Shared LLC = fast on-socket sharingThreads on the same socket exchange data through the shared L3 — much cheaper than crossing to another socket's memory.
Crossing sockets is the cliffA miss served by a remote socket costs far more. Keeping a thread near its data (affinity + first-touch) is the practical NUMA lesson — detail in Topic 6.

The exact numbers vary by CPU; the ratios are what matter for reasoning about locality.

From Sockets to Nodes to Clusters

CoreOne instruction stream + private L1/L2. The unit of a thread.
Socket / CMPSeveral cores + shared L3 + local DRAM. One NUMA domain.
NodeOne or more sockets (CC-NUMA) + often GPUs + a NIC. One OS image; the unit of an MPI rank set.
RackMany nodes + top-of-rack switch.
Cluster / SupercomputerThousands of nodes joined by a high-speed interconnect; the whole Top500 machine.
Nested parallelismSIMD lanes ⊂ core ⊂ socket ⊂ node ⊂ cluster. Each level has its own tool.
Two-level programmingMPI across nodes (distributed memory) + OpenMP / CUDA within a node (shared memory / accelerator). This "MPI+X" hybrid is the dominant HPC pattern.

Interconnects — A Preview

Once memory is distributed, performance is decided by the network that joins nodes (and sockets, and GPUs). Two things matter:

LatencyTime for a small message to arrive — dominates fine-grained communication & synchronization.
BandwidthBytes/sec for large transfers — dominates bulk data movement (halo exchange, all-to-all).
Topologies you'll meetBus, ring, mesh / torus, hypercube, fat-tree, dragonfly — each trades cost against diameter & bisection bandwidth.
Full treatment: Topic 9Interconnection networks — topology, routing, and how they cap the scalability of your MPI program — are a whole later lecture. Keep them in mind as the "glue" of every loosely-coupled machine.
Just plant the flag here. The point is that the memory-organization choice (distributed) forces a network, and the network's latency/bandwidth become first-order performance factors. We quantify topologies, bisection bandwidth, and routing in Topic 9.

Lecture 1 Capstone: One Machine, Every Class

A real supercomputer today is all of Flynn's classes at once, layered:

  • MIMD cluster — thousands of independent nodes (distributed memory, MPI).
  • Each node = multicore CC-NUMA shared memory (OpenMP within the node).
  • Each core has SIMD vector units (AVX-512 / SVE).
  • Each node hosts SIMT GPUs — thousands of data-parallel lanes.
Why no single API sufficesYou compose them: MPI + OpenMP + CUDA, each matched to a level of the hierarchy.
One machine: MIMD + SIMD + SIMT, shared & distributed memory.
This closes Lecture 1. Everything so far assumed shared memory "just works." Lecture 2 pays that debt: the moment several caches hold copies of the same shared line, the hardware owes us a coherence and a consistency guarantee — and understanding those is what keeps shared-memory code correct.

Cache Coherence & Memory Consistency

Two Guarantees Shared Memory Owes You

Cache coherence"Do all cores agree on the value of one location?" A per-address guarantee about propagating and ordering writes to a single variable.
Memory consistency"In what order do writes to different locations become visible?" The contract about ordering across variables.
Scope of this lecture — introductoryWe build the architectural view: why each is needed and how it's provided at a high level. The detailed MESI protocol, snooping state machines, and cache internals are developed in Topic 6 (Cache & Memory) — we won't duplicate them here.
Set expectations up front: this is the conceptual, architectural treatment. Students should leave able to state the coherence problem, the two coherence properties, the snooping-vs-directory distinction, and the sequential-vs-relaxed consistency idea — plus why fences/atomics exist. The gritty protocol transitions are Topic 6's job.
Module 4
Cache Coherence — Why & How

The Coherence Problem

The setupEach core has a private cache but they share one address space. Caching a shared variable makes multiple copies of the same location.
The bugIf one core writes its copy and the others keep their stale copies, the cores now disagree about the value. The shared-memory illusion is broken.

Uniprocessors never had this problem — there was only one copy of each location.

Two cached copies, one written — now they diverge.
This is the canonical failure from CSC 506 chap6: P1 and P2 both load sum=0, each writes back its own dirty value, and neither sees the other's update. Note it happens with both write-back and write-through caches (write-through updates memory but leaves the other cache stale). The only way to avoid it without a protocol is to not cache shared data — which destroys performance.

Coherence: The Two Properties

Write propagationA value written in one cache must reach the other caches — by updating or invalidating their copies.
Write serializationSuccessive writes to the same location are seen in the same order by all caches — everyone agrees on one global order.
Why serialization mattersIf two cores write x and two other cores observe those writes in different orders, they'd settle on different final values of x. The system would be incoherent. Only writes need ordering; read-vs-read can be freely reordered.
A coherence protocol guarantees bothDoable in hardware or software, but software has very high overhead — so real machines do it in hardware. Two families of mechanism follow.
Straight from CSC 506 chap6's "two properties" slide. Propagation = the new value gets out; serialization = everyone sees writes to a given address in one agreed order. A write must appear atomic and its completion must be detectable. These two properties are the definition of coherence.

Providing Coherence: Snooping vs. Directory

Snooping (broadcast)Every cache watches (snoops) a shared bus. On a write, the writer broadcasts; others invalidate (or update) their copy. The bus provides the global write order for free.
  • Simple, low latency for few cores
  • Doesn't scale — broadcast & bus bandwidth saturate
  • Natural fit for a bus-based UMA/SMP
Directory-basedA directory tracks, for each line, which caches hold a copy. On a write, the directory sends point-to-point invalidations only to the sharers — no broadcast.
  • More state & latency per access
  • Scales to many sockets/nodes
  • The mechanism behind CC-NUMA
Two ways to propagate a writeInvalidate (kill other copies; next read re-fetches) is by far the common choice; update (push the new value into other copies) is rarer. Either satisfies write propagation.
Protocol details → Topic 6The MESI states (Modified/Exclusive/Shared/Invalid) and their transitions are the implementation of snooping coherence — covered in Cache & Memory, not repeated here.
Keep this conceptual. Snooping = broadcast, great for a bus, caps out at a few dozen cores. Directory = keep a list of sharers and message only them, which is what lets CC-NUMA scale to many sockets and what big shared-memory machines use. MESI is the concrete snooping protocol; explicitly defer it to Topic 6 so we don't duplicate.
Module 5
Memory Consistency Models

From One Datum to Many

Coherence is per-addressCache coherence only governs propagation and ordering of accesses to a single memory location.

Is there any need to order accesses to multiple, different data items?

YesPrograms rely on ordering between distinct variables (e.g. "set the data, then set the ready flag"). Guaranteeing that cross-address ordering is the job of the memory consistency model.
The pivot from coherence to consistency. Coherence never says anything about how a write to x orders against a write to y. That cross-variable ordering is what programs actually depend on, and it's a separate hardware property: the memory consistency model.

The Flag Idiom — Why Ordering Matters

P0 — producer

S1: datum = 5;
S2: ready = 1;
P1 — consumer

S3: while (!ready) {};
S4: print datum;

Correctness needs S1 before S2 and S3 before S4.

  • If S2 is seen before S1 → P1 prints garbage.
  • If S4 runs before S3 → P1 reads before it is ready.
The trapEven if P0 executes S1 before S2, P1 does not necessarily see them in that order on a real multiprocessor — hardware & compilers reorder independent accesses.
The producer/consumer flag is the canonical consistency example (CSC 506 chap6, common in DOACROSS / DOPIPE). Coherence is satisfied — each of datum and ready is individually coherent — yet the program is still wrong if the two writes become visible out of order. That's a consistency issue, not a coherence one.

Sequential Consistency vs. Relaxed Models

Sequential consistency (SC)The intuitive model (Lamport): every processor's accesses happen in program order, and all processors see one global interleaving of them.

✗ SC is expensive — it forbids almost every load/store reordering, store buffering, and many compiler optimizations.

Relaxed / weak modelsReal hardware relaxes some orderings for speed (e.g. x86 TSO lets a load pass an earlier store; ARM/POWER are weaker still). The consistency model is the contract: which orderings the hardware does and doesn't guarantee.
  • Programmers must write code that conforms to the model
  • Misreading it → subtle, timing-dependent bugs
  • A source of non-portability across machines
SC is the mental model everyone assumes and almost no fast machine actually provides. The spectrum: SC (strongest) → x86-TSO → ARM/POWER weak. The weaker the model, the more reordering the hardware may do, and the more explicit ordering the programmer must request. Keep it introductory — no need to enumerate every relaxation.

Fences & Atomics — Getting Order Back

Memory fence / barrierAn instruction that forbids reordering across it — all memory ops before the fence complete (become visible) before any after it.
AtomicsRead-modify-write ops (compare-and-swap, fetch-and-add) that are indivisible and carry ordering guarantees — the building blocks of locks.
You rarely write fences by handThey're inserted for you by higher-level synchronization:
  • OpenMP barriers, critical, flush
  • Locks / mutexes (pthreads)
  • C11 / C++11 atomic with a memory order

Rule: if two threads share mutable data, synchronize — don't rely on a particular hardware ordering.

Fixing the flag idiomPublish datum, insert a release fence, then set ready; the consumer does an acquire load of ready before reading datum. The fences restore the order the relaxed model dropped.
Close the loop: relaxed models drop ordering for speed; fences and atomics let the programmer ask for exactly the ordering they need, where they need it. The practical takeaway for a CSC 548 student is that they'll almost never write a bare fence — OpenMP, locks, and language atomics do it — but they must understand that unsynchronized shared-memory code is undefined for a reason.
