Parallel I/O

Why storage is the wall — parallel file systems, MPI-IO, collective I/O, file views & high-level libraries (HDF5, NetCDF, ADIOS)
This lecture is the storage half of the performance story. Compute and communication get fast, but if every process funnels data through one serial stream the application stalls at the I/O wall. We motivate parallel file systems (Lustre, GPFS) and their striping model, then spend most of the time on MPI-IO: open/read_at/write_at, individual vs. collective calls, and file views built from derived datatypes. We close with the high-level libraries and a short best-practices checklist.

Module 1
The I/O Bottleneck & Parallel File Systems

By the end you can…

  • Explain why storage is often the performance wall in HPC
  • Describe how a parallel file system stripes a file across OSTs
  • Read and set Lustre striping with lfs

What & Why: Parallel I/O

Parallel I/OMultiple processes of one parallel program read/write a common file at the same time.

Performance: aggregate bandwidth far beyond one serial stream.
Management: a single output file is easy to archive, post-process and restart from — and is independent of the process count.

The wallCPUs and networks scale; spinning/flash storage does not. Naive serial I/O quickly dominates wall-clock time.
All processes share one file.

Parallel File Systems

Server-side viewParallel I/O = simultaneous transfer from many storage servers. One logical file is spread across many disks.

Widely deployed: Lustre, GPFS, PVFS, Ceph, BeeGFS, Google File System. They separate metadata (where the bytes live) from data (the bytes themselves) so both scale independently.

Key ideaBandwidth comes from parallelism in the storage tier, not from a faster single disk.

Striping: How One File Spans Many OSTs

A file is cut into fixed-size stripes dealt round-robin across a set of OSTs (object storage targets). Two knobs:

stripe sizebytes written to one OST before moving to the next (Lustre default ~1 MB).
stripe counthow many OSTs the file spans (default often 1–2; -1 = all).

Striping is set when the file is created and cannot change afterward.

Controlling Striping: lfs

Set & show stripe layout

# size  start  count
lfs setstripe -S 1M -i -1 -c 4 mydir
#   -S 1M : 1 MB stripe size
#   -i -1 : let system pick first OST
#   -c 4  : stripe over 4 OSTs

lfs getstripe --verbose myfile
#   lmm_stripe_count: 4
#   lmm_stripe_size:  1048576

lfs df          # per-OST capacity / usage
SituationStriping rule of thumb
One large filestripe over all OSTs
Many files (≳ 2× #OSTs)turn striping off (count = 1)
Many clients, one filedo stripe (spread the load)
Few clients, big chunksstripe over enough OSTs to stay busy
GoalKeep all OSTs occupied without creating directory or block-boundary contention.

Module 1 — Review

1. Where does a parallel file system's bandwidth come from?

From striping one file across many OSTs so several storage servers transfer data simultaneously — not from a single faster disk.

2. You have 10,000 ranks each writing its own small file. Stripe count?

1 (no striping). With far more files than OSTs, keep each file on a single OST to avoid directory and metadata contention.

File-per-Process vs. Single Shared File

N files (one per rank)Simple, no coordination, good small-scale bandwidth — but thousands of files stress metadata & directories, and post-processing must stitch them back together.
1 shared fileSingle artifact, easy to manage and restart, layout independent of #ranks — but ranks contend for the file and at block boundaries.
Hybrid: k files, l ranks eachThe middle ground: low directory contention, low per-file contention, low block-boundary contention. The practical choice at large scale (a.k.a. subfiling).
PatternDir.File
N fileshighlow
1 filelowhigh
Hybrid (k files)lowlow

Independent vs. Collective I/O

IndependentEach process states only what it will do. The file system cannot see relationships between separate processes' requests → many small scattered accesses.
CollectiveAll processes in the communicator call together. The library sees the aggregate access and can merge it into a few large, aligned transfers.

MPI-IO — the Programming Interface

By the end you can…

  • Use individual pointers, explicit offsets & nonblocking I/O

MPI-IO Background

Where it came fromSnir et al. (IBM, 1994) explored MPI as a context for parallel I/O; the MPI-IO group joined the MPI Forum in 1996.
StandardizedMPI-IO is Chapter 9 of MPI-2 (1997) — a portable, parallel read/write API with collective operations and derived-datatype file views.

What MPI-IO gives you over POSIX:

  • Open a file collectively across a communicator
  • Express noncontiguous access in one call (derived datatypes)
  • Collective calls let the library optimize the whole access
  • Portable across every parallel file system

Simple Reads: Pointers vs. Offsets

Individual file pointer + seek

MPI_File fh;  MPI_Status status;
int *buf, nints;

bufsize = FILESIZE / nprocs;
nints   = bufsize / sizeof(int);

MPI_File_open(MPI_COMM_WORLD, "/pfs/datafile",
    MPI_MODE_RDONLY, MPI_INFO_NULL, &fh);
MPI_File_seek(fh, rank * bufsize, MPI_SEEK_SET);
MPI_File_read(fh, buf, nints, MPI_INT, &status);
MPI_File_close(&fh);
Explicit offset (no seek)

MPI_File_open(MPI_COMM_WORLD, "/pfs/datafile",
    MPI_MODE_RDONLY, MPI_INFO_NULL, &fh);

MPI_File_read_at(fh, rank * bufsize,
    buf, nints, MPI_INT, &status);

MPI_File_close(&fh);

Each rank reads its own chunk of the common file. _at folds the offset into the call — thread-safe and no separate seek.

Writing & Nonblocking I/O

WritingUse MPI_File_write / write_at with MPI_MODE_WRONLY or RDWR; add MPI_MODE_CREATE if the file may not exist.

MPI_File_open(MPI_COMM_WORLD, "out",
    MPI_MODE_CREATE | MPI_MODE_WRONLY,
    MPI_INFO_NULL, &fh);
MPI_File_write_at(fh, rank*bufsize, buf,
    nints, MPI_INT, &status);
NonblockingLike nonblocking communication: start the I/O, overlap with compute, then MPI_Wait.

MPI_Request request;
MPI_File_iwrite_at(fh, offset, buf,
    count, MPI_INT, &request);

for (i = 0; i < 1000; i++) {
    /* overlap: do computation */
}
MPI_Wait(&request, &status);

Collective I/O: the _all Calls

Why collectiveA critical optimization. Every rank states only its own access, but the library sees the whole picture and builds large transfers (2-phase I/O: communicate, then read/write).

The _all suffix means all processes in the communicator passed to MPI_File_open call it — an implicit synchronization.

IndependentCollective
MPI_File_readMPI_File_read_all
MPI_File_read_atMPI_File_read_at_all
MPI_File_writeMPI_File_write_all
MPI_File_write_atMPI_File_write_at_all
RuleIf all ranks do I/O in a phase, prefer the collective form — it is usually much faster on a shared file.

Module 3 — Review

1. What does MPI_File_read_at do that MPI_File_read needs a second call for?

It takes the offset as an argument, so no separate MPI_File_seek is needed — and it is safe under concurrency since no shared pointer is mutated.

2. Why does MPI_File_write_all usually beat MPI_File_write on a shared file?

It is collective: the library aggregates all ranks' requests (2-phase I/O) into a few large, aligned transfers instead of many small scattered ones.

Noncontiguous Access & File Views

Distributed arrays land in the file in pieces — each process owns scattered regions. MPI-IO can describe these noncontiguous accesses (in memory, in file, or both) with a single call using a derived datatype.

File viewMPI_File_set_view assigns each process the portion of the file it may see — set by a triplet:
  • displacement — bytes skipped from start of file
  • etype — basic unit of access (e.g. MPI_INT)
  • filetype — which slices of the file are visible here

Building Datatypes: contiguous & vector

Contiguous — N in a row

MPI_Datatype newtype;
MPI_Type_contiguous(2, MPI_INT, &newtype);
MPI_Type_commit(&newtype);   /* required! */
Vector — blocks with a stride

/* count blocks, blocklen each,
   stride elements apart           */
MPI_Type_vector(2, 3, 5, MPI_INT, &newtype);
/* count=2, blocklen=3, stride=5   */
MPI_Type_commit(&newtype);

A vector type captures a regular strided pattern: count blocks of blocklen elements, each block starting stride elements after the last.

Always commitA derived datatype must be passed to MPI_Type_commit before use, and freed with MPI_Type_free when done.

A Simple File View (write)


MPI_File thefile;
for (i = 0; i < BUFSIZE; i++)
    buf[i] = myrank * BUFSIZE + i;          /* this rank's data */

MPI_File_open(MPI_COMM_WORLD, "testfile",
    MPI_MODE_CREATE | MPI_MODE_WRONLY, MPI_INFO_NULL, &thefile);

/* displacement = myrank*BUFSIZE ints; etype = filetype = MPI_INT */
MPI_File_set_view(thefile, myrank * BUFSIZE * sizeof(int),
    MPI_INT, MPI_INT, "native", MPI_INFO_NULL);

MPI_File_write(thefile, buf, BUFSIZE, MPI_INT, MPI_STATUS_IGNORE);
MPI_File_close(&thefile);

Each rank's view starts at its own displacement, so the same simple write lands each block in the right place — the file ends up in rank order.

A Noncontiguous File View

Goal: this process sees 2 ints, then a 4-int gap, repeating. Build it from a contiguous pair whose extent is resized to 6 ints, so the gap is baked in.

resizeMPI_Type_create_resized changes a type's extent (lower bound + total span) without changing its content — that is what creates the stride.

MPI_Aint lb, extent;
MPI_Datatype etype, filetype, contig;
MPI_Offset disp;

MPI_Type_contiguous(2, MPI_INT, &contig);
lb = 0;  extent = 6 * sizeof(int);
MPI_Type_create_resized(contig, lb, extent,
    &filetype);
MPI_Type_commit(&filetype);

disp  = 5 * sizeof(int);
etype = MPI_INT;
MPI_File_open(MPI_COMM_WORLD, "/pfs/datafile",
    MPI_MODE_CREATE | MPI_MODE_RDWR,
    MPI_INFO_NULL, &fh);
MPI_File_set_view(fh, disp, etype, filetype,
    "native", MPI_INFO_NULL);
MPI_File_write(fh, buf, 1000, MPI_INT,
    MPI_STATUS_IGNORE);

Distributed Arrays: darray

A 2-D global array block-distributed over a process grid maps to scattered file regions. MPI_Type_create_darray builds the filetype for you — describe the global array and the decomposition, and one collective write stores it all.


int gsizes[2]  = { m, n };          /* global */
int distribs[2]= { MPI_DISTRIBUTE_BLOCK,
                   MPI_DISTRIBUTE_BLOCK };
int dargs[2]   = { MPI_DISTRIBUTE_DFLT_DARG,
                   MPI_DISTRIBUTE_DFLT_DARG };
int psizes[2]  = { 2, 3 };          /* proc grid */


MPI_Comm_rank(MPI_COMM_WORLD, &rank);
MPI_Type_create_darray(6, rank, 2, gsizes,
    distribs, dargs, psizes,
    MPI_ORDER_C, MPI_FLOAT, &filetype);
MPI_Type_commit(&filetype);

MPI_File_open(MPI_COMM_WORLD, "/gpfs/datafile",
    MPI_MODE_CREATE | MPI_MODE_WRONLY,
    MPI_INFO_NULL, &fh);
MPI_File_set_view(fh, 0, MPI_FLOAT, filetype,
    "native", MPI_INFO_NULL);
MPI_File_write_all(fh, local_array,
    local_size, MPI_FLOAT, &status);
MPI_File_close(&fh);

Module 4 — Review

1. What three things define a file view, and what does each do?

displacement (bytes skipped at the start), etype (basic access unit), filetype (which slices of the file this process can see). Together they let each rank "see" only its scattered regions.

2. Why resize a contiguous type when building a strided filetype?

Resizing the extent larger than the data leaves a gap after each block — so the type repeats with a stride, producing the noncontiguous pattern without writing the gap.

The I/O Software Stack

Each layer adds structure and hands the big picture down to the next:

  • POSIX — raw read/write, no format.
  • MPI-IO — parallel API + collectives, still no format.
  • HDF5 / NetCDF / ADIOS — API plus a self-describing, portable on-disk format. Most build on MPI-IO underneath.
Self-describingThe file carries its own dimensions, types & metadata — readable by any tool, on any machine, years later.

HDF5 · NetCDF · ADIOS

HDF5Hierarchical Data Format. Groups & datasets in a file-system-like tree; rich types, chunking & compression; parallel HDF5 runs on MPI-IO.
NetCDF / pNetCDFNetwork Common Data Form — array-oriented, big in climate/weather. Parallel-NetCDF adds collective parallel access.
ADIOSAdaptable IO System — built on MPI-IO; an XML/external config selects the I/O method without recompiling.
Why use themYou write in terms of arrays and variables, not byte offsets; the library handles layout, portability & metadata — and still gets parallel performance via MPI-IO.

Best Practices

Rules of Thumb for Fast Parallel I/O

1 · Go big & contiguousFew large transfers beat many small ones — metadata and seek overhead dominate small accesses.
2 · Use collective I/OPrefer the _all calls on a shared file; 2-phase I/O aggregates ranks into large writes.
3 · Describe noncontiguityUse file views / derived datatypes so one call passes the whole pattern to the library.
4 · Align to stripesMatch access size & offsets to the stripe size so a rank's writes don't straddle OST boundaries.
5 · Set striping deliberatelyOne big file → stripe over all OSTs; many small files → don't stripe. Set it at create time.
6 · Move up the stackLet HDF5 / NetCDF / ADIOS handle layout & portability when you can.

Stripe Alignment, Visually

UnalignedA rank's block crosses a stripe boundary → the write touches two OSTs and both must coordinate at the shared block. Contention & serialization.
AlignedEach rank's access starts on a stripe boundary and is a multiple of the stripe size → one OST per rank, no boundary contention.
