Fault Tolerance & Resilience

Why big machines fail, and how programs survive it
Instructor: Jiajia Li

At leadership scale, failure stops being a rare event and becomes part of the steady-state operating condition. This deck takes a programming/systems view: we start with why system MTBF collapses as you add nodes, build up checkpoint/restart (the workhorse), then go beyond rollback (replication, ABFT), and finish by looking at how resilience shows up across the stack you already know — MPI, Spark, and deep-learning training.

Module 1
Why Resilience?

The Scale Problem: System MTBF

Key intuitionOne node may run for years between failures, but a machine is only "up" when all its nodes are. With independent failures, the system MTBF shrinks linearly with node count.
\( \mathrm{MTBF}_{sys} \approx \dfrac{\mathrm{MTBF}_{node}}{N} \)

Node MTBF = 5 years; N = 100,000 nodes → MTBFsys ≈ 26 minutes. Something is always broken.

More nodes → far shorter time between failures.

Faults, Errors, Failures — and a Taxonomy

fault → error → failure

Fault — the root cause (a bit flips, a DIMM degrades).
Error — the fault corrupts a value or state.
Failure — the error becomes externally visible (wrong result, crash).

A fault is not always a failureAn error may be masked (ECC corrects it) and never surface. Resilience is about stopping the fault→error→failure chain.
AxisOptions
Durationtransient (one-off bit flip) vs permanent (dead node/disk)
Symptomfail-stop (node halts, obvious) vs silent (SDC — bad data, no crash)
Detectiondetected (we know) vs undetected (we don't)
The scary quadrantSilent + undetected = SDC: the job finishes and hands you a wrong answer. Fail-stop is easy by comparison.

Two Recovery Philosophies

Rollback recoveryPeriodically save state; on failure, restore the last good checkpoint and re-execute the lost work.

+ General — works for almost any application.
− Wastes the work since the last checkpoint; needs storage & I/O bandwidth.

Checkpoint/restart, message logging.

Forward recoveryCarry enough redundancy that you can repair the error in place and keep going — never go back.

+ No lost work, no rollback latency.
− Application-specific or needs extra resources (replicas, checksums).

Replication/voting, ABFT, Spark lineage recompute.

Through the deckModules 2 is rollback; Module 3 is mostly forward; Module 4 shows both philosophies in real systems.
Module 2
Checkpoint / Restart — the Workhorse

Coordinated Checkpointing

IdeaAll ranks synchronize at a barrier and write a globally consistent snapshot to the parallel file system. On any failure, the whole job restarts from the last snapshot.

Simple and recovery is easy — the saved state is consistent by construction. But every rank dumps memory to the PFS at the same time: this is the #1 driver of parallel I/O bandwidth on HPC systems.

Cross-link → io deckCheckpoint writes are the canonical bursty, write-heavy collective I/O workload — see the Parallel I/O deck (MPI-IO, collective buffering, the PFS).
Synchronized write; on crash, everyone rolls back together.

Uncoordinated Checkpointing & the Orphan Problem

IdeaEach rank checkpoints independently, on its own schedule — no global barrier, less synchronization cost.
The catch: in-flight messagesIf rank A's checkpoint is after sending a message but rank B's is before receiving it, the global state is inconsistent.

Orphan message — received but the send was never recorded (a "received-from-nowhere" message after rollback). Lost message — sent but the receive is undone. Naïve rollback can cascade — the domino effect — undoing far more than intended.

Inconsistent cut: a message recorded on one side only.

How Often to Checkpoint? — Young / Daly

The trade-offToo often → you burn I/O bandwidth writing checkpoints you never use. Too rarely → each failure throws away more recomputed work. There is a sweet spot.
\( \tau_{opt} \approx \sqrt{2\,C\,M} \)

C = cost (time) to write one checkpoint; M = system MTBF. (Young 1974; Daly 2006 adds higher-order & restart terms.)

Note the dependenceAs M shrinks with scale (Module 1), τopt shrinks too — big machines must checkpoint more often, which strains the very I/O system already under load.
Worked example
QuantityValue
Checkpoint cost C1 min
System MTBF M4 h = 240 min
τ = √(2·C·M)√(2·1·240) ≈ 22 min

So checkpoint roughly every 22 minutes. Halve the MTBF (more nodes) and the interval drops to ≈ 15 min; make checkpoints 4× cheaper and it rises to ≈ 44 min.

Wasted time per failure ≈ ½·τ (expected lost work) + C (the write). Minimizing total overhead yields the √ formula.

Multi-Level & Asynchronous Checkpointing

InsightMost failures are local (one node, one process). You don't need the slow global PFS for those — keep cheap checkpoints close, escalate only when you must.

L1 — node-local NVMe / RAM: fastest, survives a process crash.
L2 — partner / XOR-encoded across neighbors: survives a node loss.
L3 — parallel file system: survives a whole-system failure, but slowest.

Burst buffersA node-local or near-node NVMe tier absorbs the checkpoint write at memory-like speed; data drains to the PFS asynchronously, overlapping the next compute phase. Libraries: SCR, FTI, VeloC.
Cheap local checkpoints; escalate only as needed.

Message Logging & Rollback-Recovery

IdeaCombine occasional checkpoints with a log of messages. After a crash, restore the checkpoint and replay the logged messages to deterministically re-reach the failure point — only the failed process re-executes.

Rests on the piecewise-deterministic assumption: between received messages, a process behaves deterministically, so replaying the same message sequence reproduces the same state.

Pessimistic loggingLog (and acknowledge) each message before delivering it. Clean recovery, no orphans — but higher per-message latency.
Optimistic loggingLog asynchronously (lower overhead), accepting that a few un-logged messages may be lost on failure, requiring some rollback.
Why botherAvoids forcing all ranks to roll back — only the crashed rank replays, which matters at very large scale.
Module 3
Beyond Rollback

Replication

Active replicationRun two (or three) copies of each process in lock-step. A failure is masked instantly — the survivor keeps going; with three copies you can vote to also catch SDC.
Passive replicationA standby copy receives state updates and takes over only on failure — lower steady-state cost, some failover latency.
The costDual replication halves usable machine throughput (2× resources for 1× work). It only pays off when checkpoint/restart can't keep up.
When replication winsAt extreme scale, when MTBF drops so low that the machine spends more than ~50% of its time checkpointing and recomputing — then paying 2× to almost never roll back is the better deal.

Rule of thumb: checkpointing is cheaper until the failure rate gets high enough that rollback overhead exceeds the cost of a redundant copy.

Proactive / Prediction-Based Resilience

IdeaDon't wait for the crash — predict it. Health monitoring (temperatures, ECC-correctable-error rates, fan/PSU telemetry, SMART data) flags a node that is about to fail.

On a prediction, migrate the process off the suspect node to a spare before it dies — no rollback, no lost work. This is forward recovery driven by anomaly detection / ML on telemetry.

Best as a complementPredictors miss surprises, so proactive migration reduces the failure rate the checkpoint system must absorb — it doesn't replace checkpointing.
Predict, then pre-emptively migrate.

ABFT — Algorithm-Based Fault Tolerance

IdeaEncode redundancy in the data itself, so the algorithm can detect — and often locate and correct — a corrupted value without any rollback. The classic case is dense linear algebra.

Matrix-multiply checksums. Augment A with a row-checksum column (each row's element sum) and B with a column-checksum row. Then in C = A·B, the checksum row/column are preserved by the multiply:

\( \sum_j C_{ij} = C^{r}_i,\qquad \sum_i C_{ij} = C^{c}_j \)

After the multiply, recompute each row/column sum and compare to the stored checksum. A mismatch in row i and column j pinpoints the bad entry Cij; the checksum difference gives the correction to add back.

Cross-link → Linear Algebra advanced topicABFT lives inside the matmul/factorization kernels covered there; it recovers in place, complementing checkpoint/restart.
Checksum row + column locate the bad entry.

Detecting Silent Errors (SDC)

The hard partSDC produces no crash, so checkpoint/restart alone can't help — you can't restart what you don't know is wrong. You must add explicit detection.
Replication / votingRun 2 copies and compare (detect) or 3 copies and vote (detect + mask). General, but 2–3× cost.
Algorithmic checksCheap, problem-specific invariants: ABFT checksums; residual checks (does ‖Ax − b‖ stay small?); energy/mass conservation in a simulation; monotonicity bounds.
Layered detectionECC/parity catches most hardware bit flips in memory; algorithmic checks catch the rest cheaply; replication is the expensive backstop for the highest-assurance work.

A flagged but uncorrectable error can fall back to rollback — detection turns a silent error into a recoverable fail-stop.

Module 4
Resilience Across the Stack

MPI Fault Tolerance & ULFM

Default MPIThe standard error handler is MPI_ERRORS_ARE_FATAL: a process failure aborts the whole job. The communicator state after a failure is undefined — you cannot safely keep using it.
ULFM — User-Level Failure MitigationAn MPI extension that lets the application survive a process loss and decide what to do:
  • MPIX_Comm_revoke — invalidate a broken communicator everywhere so no rank hangs in a collective.
  • MPIX_Comm_shrink — build a new communicator with the dead ranks removed.
  • MPIX_Comm_agree — fault-tolerant agreement so survivors reach a consistent decision.
Cross-link → mpi deckThis builds directly on communicators & collectives — ULFM repairs the communicator, then you re-load from a checkpoint and continue.
ULFM-style recovery sketch (C)

/* install a non-fatal error handler */
MPI_Comm_set_errhandler(comm,
    MPI_ERRORS_RETURN);

rc = MPI_Allreduce(&local, &sum, 1,
        MPI_DOUBLE, MPI_SUM, comm);

if (rc != MPI_SUCCESS) {
  /* a rank died: stop the bleeding... */
  MPIX_Comm_revoke(comm);

  /* ...rebuild without the dead ranks */
  MPIX_Comm_shrink(comm, &newcomm);

  /* agree we are all recovering */
  int flag = 1;
  MPIX_Comm_agree(newcomm, &flag);

  comm = newcomm;             /* continue */
  reload_from_checkpoint(comm);
}

Handler returns instead of aborting → revoke → shrink → agree → keep going on the smaller communicator.

Spark Lineage — Recompute, Don't Restart

A different modelSpark records each RDD's lineage: the deterministic sequence of transformations (the DAG) that built it from its parents. It does not take global checkpoints.

When a partition is lost (an executor dies), Spark recomputes just that partition from its parent partitions, following the lineage. Recovery is uncoordinated and local — no rollback of healthy partitions, no synchronized snapshot.

Cross-link → bigdata deckThis is forward-style recovery enabled by deterministic, coarse-grained transformations on immutable RDDs — contrast with HPC coordinated checkpoint/restart. (Long lineages are pruned with explicit checkpoint().)
Lineage DAG: one lost partition, recomputed.

Deep-Learning Checkpointing

What gets savedA training checkpoint must capture model weights + optimizer state (e.g. Adam's moment estimates) + step count + RNG/data-loader position — enough to resume bit-for-bit.

DDP / DeepSpeed checkpoint periodically; DeepSpeed/ZeRO shards optimizer state across ranks, so each rank writes only its shard. Frameworks now support asynchronous checkpointing: snapshot to host memory, then write to storage in the background, overlapping the next training step.

Why it is existential hereTraining a frontier model runs for days to weeks on thousands of GPUs. By Module 1, the MTBF of that many GPUs is hours — a failure is guaranteed. Without frequent checkpoints you lose days of compute.
Cross-link → nn deckSame checkpoint/restart and Young/Daly interval logic from Module 2 — but the "state" is the model + sharded optimizer, and the writes are huge. Checkpoint cadence is a first-class training hyperparameter.

Fault Tolerance — Big Picture

Checkpoint / restartGeneral-purpose, fail-stop. Default for HPC & DL training. Tune the interval with √(2CM); use burst buffers & multi-level to cut C.
ReplicationWhen MTBF is so low that rollback overhead > the cost of a redundant copy; also gives voting against SDC. Pays 2–3×.
ABFT / algorithmicWhen the kernel has structure (linear algebra). Detects, locates, corrects in place — forward recovery, low overhead.
Lineage / recomputeWhen work is deterministic & coarse-grained (Spark). Recompute the lost piece from its parents — no global checkpoint.
One sentence Match the mechanism to the failure model and the cost of lost work: roll back when state is opaque, go forward (ABFT, replication, lineage) when the data or the computation gives you the redundancy to repair in place.
