Module 1
Motivation — Processing Data at Scale

What Makes It "Big Data"?

Out-of-coreThe data cannot fit in one machine's memory — or even on one disk. Think the whole Web: billions of pages.

Bulk, highly parallel processing: lots of independent tasks. This differs from classic HPC, where tasks are tightly dependent and communicate constantly.

BottleneckPerformance is limited by I/O and network bandwidth, not by floating-point throughput.
Good fitsTerm frequencies across the Web; URL access counts; building a reverse web-link graph; sort.
Poor fitsSmall data; tightly-coupled, highly-dependent computation; finding a single record; low-latency queries.

Scale-Up vs. Scale-Out

Scale-up (vertical)One bigger box — more cores, more RAM, faster disks. Simple, but bounded and expensive at the top end.
Scale-out (horizontal)Many commodity machines cooperating. Add nodes to add capacity; expect — and tolerate — failures.

Big data picks scale-out: hardware is cheap, datasets are enormous, and at 1000s of nodes something is always failing.

Add nodes, not a bigger box.

The Distributed File System

Bulk processing needs the data spread across the cluster so many workers can read in parallel. That is the job of a parallel/distributed file system (PFS/DFS).

Two worldsHPC: PVFS, Lustre, BeeGFS.   Big Data: Google FS (GFS), HDFS.
Key ideasSplit each file into large blocks; replicate blocks across nodes; expect failures and recover automatically.
Blocks + replicas = parallel reads & fault tolerance.
Module 2
The MapReduce Programming Model

MapReduce — the Big Idea

A programming model (Dean & Ghemawat, Google, OSDI 2004) for processing large distributed datasets on a cluster of commodity machines.

mapApplied to each input record; emits intermediate key/value pairs.
map: (k1,v1) -> list(k2,v2)
reduceMerges all values that share an intermediate key.
reduce: (k2,list(v2)) -> list(v2)
Bag-of-tasks 1. Map tasks assigned to workers
2. Shuffle intermediate data by key
3. Reduce tasks assigned to workers

Borrows from Lisp's map/reduce. Relatives: Pig/Pig Latin (Yahoo), Dryad (Microsoft). Re-engineered open-source as Hadoop.

Assumption: records are independent (no correlation), or the data is small.

Dataflow: Map → Shuffle → Reduce

Each map output pair is routed to the reducer responsible for its key; reducers sort and group their input, then process one group at a time.

Canonical Example: Word Count

map & reduce (pseudocode)

# key: document name + line no
# value: the line's text
def map(key, value):
    for w in value.split():
        emit(w, "1")

# key: a word
# values: a list of counts
def reduce(key, values):
    result = 0
    for v in values:
        result += int(v)
    emit(key, result)
Input P1: the weather is good
P2: today is good
P3: good weather is good
After shuffle (grouped) good -> {1,1,1,1}
is   -> {1,1,1}
weather -> {1,1}
Outputgood 4 · is 3 · weather 2 · the 1 · today 1

Designing a MapReduce Job

mapActs on one record at a time — cannot look at other pairs. Good for filtering and for emitting several intermediate pairs per input (e.g. one (word,1) per word).
reduceAggregates — may look at many values, but only those map sent to the same key. Good for sums, counts, joins.
The key decisionChoose the intermediate key so that everything reduce must see together arrives under one key.
Stateless!No static variables, no remembering past records. There are no guarantees about which worker gets which pairs.
No DIY I/ODon't open files yourself. All input arrives as arguments; all output goes through emit.

The Runtime: Master & Workers

Three moving parts make it work:

Distributed file systemStores inputs, outputs, and temporary results across all nodes (GFS/HDFS).
Driver programRuns on one node; names the inputs/outputs, the mapper and reducer, and any custom behavior.
Runtime systemSupervises task execution across nodes (the master / JobTracker).
Master stateFor every task: state (idle / in-progress / completed), the worker handling it, and the location of map output regions to push to reducers.
Task granularityMake M map tasks and R reduce tasks ≫ #machines → dynamic load balance and faster recovery.
Cost: O(M+R) scheduling, O(M·R) state.

Fault Tolerance by Re-execution

Worker failureDetected by missing heartbeats. Completed and in-progress map tasks are re-run; in-progress reduce tasks are re-run.

Safe because tasks are idempotent — recomputing gives the same result. Completion is committed through the master.

StragglersA task taking too long is duplicated (speculative execution); first to finish wins — agnostic to the cause of the slowdown.
LocalityInput lives in GFS with several replicas. The scheduler places a task on or near a node holding the data — move computation to the data, since moving data is the expensive part.
Master failureRare; the original design simply aborts and retries the job rather than replicating the master.

Case Study: Distributed Sort

ProblemSort 1 TB = 1010 records of 100 bytes (TeraSort-style).

map:    emit(10-byte key, 100-byte record)
reduce: identity (just write through)
M = 15000   R = 4000
output: 2-way replicated (GFS redundancy)

A pre-pass MapReduce may sample keys to balance reduce partitions.

Observed • Scan 1010 records for a rare pattern (~92K hits): 150 s.
• Full sort: ~839 s.

Rates tell the story: input > shuffle > output. Reading is fast (locality); the shuffle moves data over the network; output is slowest because it writes two replicas.

Speculative backup tasks and graceful handling of machine failures keep the job's tail latency in check.

Module 3
The Hadoop Ecosystem

HDFS — Structure & Replication

The open-source counterpart of GFS: redundant storage on commodity hardware, built to expect and tolerate failures, optimized for large files and batch reads.

LayoutFiles = collections of blocks (classically 64 MB). Every block replicated on ≥ 3 nodes.
RolesNameNode holds metadata (files→blocks); SecondaryNameNode backs it up; DataNodes store & serve blocks.
Rack-aware replica placement.

HDFS — Failure Handling

Health checksDataNodes periodically check in with the NameNode to report they are alive and which blocks they hold.
On node lossThe NameNode notices missing check-ins and orders surviving DataNodes to re-replicate any now under-replicated blocks. Fail-over is automated.
What it optimizes forDurability and throughput on huge files, not low latency or small random reads. Re-replication is simple and robust — but bandwidth-hungry.

This is the classic big-data bargain: pay extra storage and network for replication, and in return survive arbitrary node and rack failures with no operator intervention.

Hadoop Jobs, Tasks & Trackers

JobA user-submitted map/reduce program.
TaskA single mapper or reducer instance. Failed tasks are retried automatically; run local to their data when possible.
JobTracker (JT)Manages job submission and delegates tasks.
TaskTrackers (TT)Ask for work and execute tasks; fetch data from a DataNode if it isn't already local.
Tasks WILL failThe JT retries a task up to N times; after N failures the whole job fails (so a deterministic bug can't loop forever).
Speculative executionThe JT may launch duplicate copies of a slow task; the first to finish wins, the rest are killed — masking a slow node.
Data localitySchedule tasks where the data already lives; moving data between nodes is assumed costly.

The Hadoop Stack

HBase: sparse NoSQL store · Pig: Pig Latin → MapReduce · Hive: SQL-like queries · Cascading: complex workflows · ZooKeeper: coordinates & monitors components.

Module 4
Apache Spark — RDDs & In-Memory Computing

Why a New Model? Data Sharing

MapReduce simplified big-data analysis — but users wanted multi-stage apps (iterative graph & ML algorithms) and interactive ad-hoc queries. Both need fast data sharing across jobs.

MapReduce wayEvery stage writes to HDFS and the next reads it back — replication + serialization + disk I/O between every iteration. Slow.
Spark wayKeep working data in distributed memory; load once, reuse across iterations and queries — 10–100× faster than going through network and disk.

Spark System & SparkContext

Driver + workersThe driver defines the computation; worker programs run on cluster nodes (or local threads) and hold the data.

Not a fork of Hadoop — a separate, fast, MapReduce-like engine that's compatible with Hadoop storage: it can read/write HDFS, HBase, SequenceFiles, and more.

RDDResilient Distributed Dataset — a distributed collection partitioned across workers, cacheable in memory, rebuilt on failure.
Create a SparkContext (Python)

from pyspark import SparkContext
sc = SparkContext(
    "masterUrl",   # cluster, or local / local[N]
    "name",        # app name
    "sparkHome",   # Spark install path
    ["library.py"] # JARs/files to ship
)

APIs in Scala, Java, Python, R. The context is the handle through which you build RDDs.

RDDs: Transformations vs. Actions

Build an RDDParallelize a collection, read a file (HDFS/S3/HBase), or transform an existing RDD. Programmer chooses #partitions.
Transformations — LAZYmap, filter, flatMap, union…
Define a new RDD but compute nothing yet — they just record what to do.
Actions — EAGERcollect, count, reduce, take…
Force evaluation: run all the pending transformations and return a result.
{1, 2, 3, 3} → transformations

rdd.map(lambda x: x + 1)    # {2,3,4,4}
rdd.filter(lambda x: x != 1)# {2,3,3}
rdd.flatMap(lambda x:        # {1,2,3,2,
            range(x,4))      #  3,3,3}
rdd.distinct()              # {1,2,3}
→ actions

rdd.collect()               # {1,2,3,3}
rdd.count()                 # 4
rdd.take(2)                 # {1,2}
rdd.reduce(lambda x,y: x+y) # 9

Why Laziness? The DAG & Lineage

Because transformations are deferred, Spark sees the whole chain before running anything. It builds a DAG of operations and optimizes it — pipelining stages, pruning, choosing where to shuffle — then executes only when an action demands a result.

Lineage = fault toleranceEach RDD remembers how it was derived from its parents. Lose a partition? Recompute just that partition by replaying its lineage — no replication needed.
Lineage DAG; runs only at the action.

Example: Log Mining (interactive)

Cache once, query many times (Scala)

val lines  = spark.textFile("hdfs://...")
val errors = lines.filter(_.startsWith("ERROR"))
val msgs   = errors.map(_.split('\t')(2))
val cached = msgs.cache()   // persist in RAM

cached.filter(_.contains("foo")).count   // action
cached.filter(_.contains("bar")).count   // action

First action loads & caches the error lines; later queries hit memory, not disk.

ResultFull-text search over 1 TB scaled data: 5–7 s (vs ~170 s on disk); cached follow-up queries in < 1 s.
cache() / persist()Each partition is kept in memory and reused by later actions on that RDD. If a cached partition is lost, lineage recomputes it.

Storage levels trade space vs. CPU vs. durability: MEMORY_ONLY, MEMORY_AND_DISK, ..._SER (serialized), ..._2 (2 replicas), DISK_ONLY.

Iterative Workloads Shine: ML

Logistic regression (Scala)

val data = spark.textFile(...)
              .map(readPoint).cache()
var w = Vector.random(D)
for (i <- 1 to ITERATIONS) {
  val gradient = data.map(p =>
    (1/(1+exp(-p.y*(w dot p.x))) - 1)
        * p.y * p.x
  ).reduce(_ + _)
  w -= gradient
}
println("Final w: " + w)
Why it's fastdata is loaded and cached once. Every iteration re-reads it from memory — no HDFS round-trip per pass like MapReduce would force.

The same pattern powers iterative graph algorithms and most machine-learning training loops — exactly the workloads that made MapReduce painful.

Word-count, Spark style 

lines.flatMap(lambda l: l.split())
     .map(lambda w: (w, 1))
     .reduceByKey(lambda a,b: a+b)

Shared Variables

Broadcast variablesSpark's version of Hadoop's DistributedCache. A read-only value cached on each node; Spark distributes it to minimize communication cost (e.g. a lookup table shared by all tasks).
AccumulatorsSpark's version of Hadoop's Counter. Add-only variables combined through an associative operation; native numeric types & mutable collections, extensible. Only the driver reads the value.
Why these existRDD closures are shipped to every task, so a large lookup would be copied per task. Broadcast sends it once per node; accumulators give a safe way to gather a global count/sum back at the driver without a full reduce.
Module 5
When to Use Which

MapReduce: Good, OK, Bad

Good forEmbarrassingly-parallel jobs; summing, grouping, filtering, joining; offline batch over massive data; scanning an entire dataset.
OK forIterative jobs (graph algorithms) — but each iteration reads/writes disk, so per-iteration I/O latency is high.
Bad forShared state / coordination (tasks must be share-nothing); low-latency jobs; small datasets; finding individual records.
Abstraction limitMapReduce only fits idempotent, share-nothing operations. That constraint is exactly what buys it transparent scaling and fault tolerance — but it rules out tightly-coupled algorithms.

MapReduce vs. Spark

DimensionHadoop MapReduceApache Spark
Data sharingThrough HDFS between every stageIn-memory RDDs reused across stages
Iterative / interactiveSlow — disk I/O per passFast — load once, 10–100×
Programming modelmap + reduce onlymap/reduce, DAG, streaming, vertex-based
EvaluationEager, stage by stageLazy transformations + eager actions
Fault toleranceRe-execute idempotent tasksRecompute partitions from lineage
APIsJava (Pig/Hive on top)Scala, Java, Python, R
When MapReduce still winsA single huge batch pass that streams once through data far larger than cluster memory — there's little to reuse, so Spark's in-memory edge mostly disappears.

Big Data — Big Picture

StoreSplit files into replicated blocks on a DFS (GFS/HDFS); survive node & rack failure.
Computemap per record → shuffle by key → reduce per group; move computation to the data.
RecoverRe-run idempotent tasks (MapReduce) or replay lineage (Spark) — no manual intervention.
Iterate fastSpark keeps working sets in distributed memory; lazy DAGs let it optimize before running.
ChooseBatch one-pass scans → MapReduce; iterative/interactive/ML → Spark; tiny or tightly-coupled → neither.
One sentence Express your computation as map + reduce over a replicated distributed dataset, let the framework handle distribution and failure, and cache in memory when you'll touch the data more than once.
