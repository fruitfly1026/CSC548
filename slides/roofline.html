The Roofline Model

A visual bound on attainable performance

The roofline model puts two hardware limits — peak compute and peak memory bandwidth — on one plot, and uses a kernel's arithmetic intensity to say which limit binds it. This deck builds the model, shows how to read and use it, adds the practical refinements (below-peak ceilings, the memory hierarchy), and covers how to measure the numbers and which tools draw the plot for you.

Module 1
The Model

Why a Roofline?

A kernel is limited either by how fast the cores can do arithmetic, or by how fast memory can supply operands. Peak GFLOP/s alone never tells you which.

The insightPut both limits on one plot against a single kernel property — its arithmetic intensity — and the binding limit is obvious at a glance.
What it gives you • an upper bound on performance for a given kernel;
• a verdict: memory-bound or compute-bound;
• the headroom left, and which optimization would move you.

Williams, Waterman & Patterson introduced it for multicore in 2009; it now covers CPUs, GPUs, and accelerators.

Arithmetic (Operational) Intensity

DefinitionFlops performed per byte moved from memory:
\( I \;=\; \dfrac{\text{FLOPs}}{\text{bytes moved}} \)

The classic model counts bytes to and from DRAM. A high intensity means the data is reused many times once it is on chip. A low intensity means each byte is touched briefly, then discarded.

Units: flop/byte; the original roofline paper calls it operational intensity. The algorithm and its implementation set it — the machine does not.

KernelBytes / flop≈ I
DAXPY (`y=ax+y`)high~0.06
SpMVhigh~0.17
7-pt stencilmedium~0.3–0.5
FFT—~O(log N)
Dense GEMMlow~O(N)
Reuse turns bytes into many flops → higher I.

Two Ceilings: Compute and Bandwidth

Peak compute · πThe most FLOP/s the cores can retire: cores × SIMD width × FMA × frequency. A flat, intensity-independent ceiling.
Peak bandwidth · βThe most bytes/s the memory system can deliver. It caps performance to β · I — the more intensity, the more compute β can sustain.
Combine themWhichever is smaller wins:
\( P(I) = \min(\pi,\; \beta I) \)
Why β·I If a kernel moves one byte per 1/I flops, then at bandwidth β bytes/s it can sustain at most β·I flops/s. That is the sloped roof.

The Roofline

The plotLog–log axes. The sloped roof is β·I; the flat roof is π. They meet at the ridge point.
  • Left of the ridge: bandwidth binds you.
  • Right of the ridge: compute binds you.
  • A kernel sits at its intensity; its ceiling is the roof directly above.

Ridge Point & the Verdict

Ridge pointWhere the two roofs meet:
\( I^{*} \;=\; \dfrac{\pi}{\beta} \)
The least intensity at which a kernel could still reach peak compute.
  • I < I* → memory-bound, ceiling β·I.
  • I > I* → compute-bound, ceiling π.
Ridge points keep risingModern hardware adds FLOP/s faster than bandwidth, so I* grows. Kernels that were compute-bound become memory-bound over time.

A typical CPU ridge is around 5–15 flop/byte; a GPU with HBM can be higher still. Most sparse and stencil kernels sit far to the left of it.

Module 2
Reading & Using It

Placing a Kernel

Three numbers 1. the kernel's intensity I (flops ÷ bytes);
2. its measured performance (GFLOP/s);
3. the machine's π and β.

Drop a vertical line at I. Where it meets the roof is the ceiling. Plot your measured point below it; the gap is your headroom.

What the gap tells you Close to the roof → near optimal for this intensity; to go faster you must raise the intensity.

Far below the roof → the implementation is leaving performance on the table (poor bandwidth use or poor compute use).

Worked Example: SpMV vs GEMM

SpMVTwo flops per nonzero, but each nonzero drags a value and an index and touches x irregularly.
\( I \approx \dfrac{2}{12} \approx 0.17 \)
Far left of the ridge → memory-bound. Ceiling is β × 0.17, not π.
Dense GEMMEach of the O(N³) flops reuses data that only costs O(N²) bytes, so intensity grows with the tile size.
\( I \sim O(N) \)
With blocking it crosses the ridge → compute-bound, ceiling π.
Same machine, opposite verdict The hardware is identical; intensity alone decides which roof each kernel lives under.
Module 3
Refinements

Below-Peak Compute Ceilings

Peak assumes every trick is used: full-width SIMD and fused multiply–add. Drop one and the compute roof drops with it.

  • No FMA → about half of peak.
  • No vectorization → the scalar ceiling, lower still.
  • Poor ILP or thread imbalance → lower again.
Reading themThese stacked ceilings tell a compute-bound kernel which missing feature is capping it.

Bandwidth Ceilings & the Memory Hierarchy

There is not one bandwidth but several — one per level of the hierarchy. Each level gives its own sloped roof.

  • DRAM / HBM: highest capacity, lowest bandwidth → shallowest roof.
  • L2, L1: less capacity, more bandwidth → steeper roofs.
Cache-aware rooflineMeasure intensity against a chosen level's traffic. A kernel that fits in cache rides the steeper cache roof, not the DRAM one.
Why it mattersThe DRAM roofline can look pessimistic for a cache-resident kernel, and optimistic for one that streams. Pick the level whose traffic actually dominates, and say which one you used.

Two common variants: the classic (DRAM-traffic) roofline and the cache-aware roofline (CARM), which fixes intensity to the L1/core interface.

Raising Arithmetic Intensity

Blocking / tilingReuse a tile of data many times while it is on chip. Fewer trips to DRAM per flop → higher I.
Loop fusionDo several operations in one pass over the data, instead of streaming it once per operation.
Better data structuresLayouts that improve reuse and locality (blocked/ELL sparse formats, structure-of-arrays) move bytes less often.
The move on the plotRaising I slides the kernel right along the bandwidth roof — toward and past the ridge, where compute finally becomes the limit.

Which Ceiling to Attack

Two directions Up to the roof — better use of the current limit (prefetch, unit-stride, NUMA placement, vectorize).

Right along the roof — raise intensity so a higher roof applies (tiling, fusion, reuse).

If you are already on the bandwidth roof, only raising I helps. If far below it, fix the implementation first.

Module 4
In Practice

Getting π and β

Peak compute πTheoretical: cores × SIMD lanes × 2 (FMA) × frequency. Or measured with a compute-bound micro-benchmark / LINPACK.
Peak bandwidth βRarely the spec number. Measure the achievable value with the STREAM benchmark; expect 60–85% of the datasheet peak.
Empirical Roofline ToolkitERT (LBNL) sweeps intensity with micro-kernels and draws the machine's real roofs — compute and every bandwidth level — for you.

Always draw the roof from achievable peaks. Datasheet peaks make every kernel look worse than it is.

Counting Flops and Bytes Honestly

Which bytes?Intensity depends on what you count. Algorithmic bytes (the minimum traffic) give an optimistic point; measured DRAM traffic (from counters) gives the real one.

Caches, redundant loads, and write-allocate all change the byte count. The gap between algorithmic and measured intensity is itself a locality diagnostic.

FlopsCount useful flops, consistently in the precision you run (FP64 / FP32 / FP16). Do not count masked-off or speculative work.
BytesPrefer hardware counters (DRAM read+write) over hand estimates for the measured point.

Roofline — Big Picture

ModelP = min(π, β·I); the ridge I* = π/β splits memory- from compute-bound.
ReadPlace the kernel at its intensity; the roof above is the ceiling; the gap is headroom.
RefineBelow-peak compute ceilings and per-level bandwidth roofs sharpen the diagnosis.
ActFar below the roof → fix the implementation. On the roof → raise intensity by tiling and fusion.
One sentenceFind your intensity, find the roof above it, and either climb to that roof or move right to a higher one.
