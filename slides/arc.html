Module 1
What ARC Is

By the end you can…

  • Describe ARC's login node vs. compute nodes
  • Explain why you never run real work on the login node
  • Name the Slurm commands you will use all semester

The ARC Cluster

ARCAn NCSU research cluster of GPU-equipped compute nodes, shared by many users and managed by the Slurm scheduler.

You connect to a single login node (arc.csc.ncsu.edu). From there you request compute nodes (c1, c39, …) from the scheduler — you do not ssh straight onto them.

Never compute on the login nodeIt is shared by everyone. Compile small things there; run jobs on compute nodes.
Login node is the front door; jobs run on compute nodes.

Slurm — the Commands to Memorize

CommandWhat it does
sinfoShow partitions / devices and their availability
salloc -N<#nodes> -n<#procs> -p <partition>Allocate nodes for an interactive session
squeueList jobs and their states
sbatch <script>Submit a batch job script to the queue
scancel <jobID>Cancel the job with that ID
exitRelease the node promptly when done
Don't forget theseYou will type salloc, squeue, sbatch, and scancel for the next couple of months.
Module 2
Getting On — SSH & Files

By the end you can…

  • Generate an SSH keypair on Windows or macOS/Linux
  • Log in to ARC with your Unity ID
  • Move files in and out with scp / rsync

Generate an SSH Keypair

WindowsEnable OpenSSH Client: Start → "Apps & Features" → "Optional Features" → add OpenSSH Client. Then use Command Prompt.
macOS / LinuxSSH is already installed — just open a terminal.

Keys are saved to ~/.ssh/id_rsa (private) and ~/.ssh/id_rsa.pub (public). Press Enter at every prompt to take the defaults.

Create the keypair

ssh-keygen -t rsa -b 4096
# Enter, Enter, Enter (accept defaults)

# show your PUBLIC key
cat ~/.ssh/id_rsa.pub
Public vs. privateShare the .pub file only. Never share or copy id_rsa (the private key).

Activation & First Login

Activation emailOnce your account is registered you receive an activation email. After that, your public key gets you in — no password.
Log in

ssh <unityID>@arc.csc.ncsu.edu

Replace <unityID> with your NCSU Unity ID (e.g. smanthe).

If it rejects your keyMake sure the matching public key was registered, and that permissions are tight: chmod 600 ~/.ssh/id_rsa.
Verbose debugging

ssh -v <unityID>@arc.csc.ncsu.edu 2>&1 \
  | grep -i "offering\|accepted"

Moving Files & Storage

Copy a single file up / down

# laptop  ->  ARC
scp hw0.c <unityID>@arc.csc.ncsu.edu:~/hw0/

# ARC  ->  laptop
scp <unityID>@arc.csc.ncsu.edu:~/hw0/out.txt .
Sync a whole directory

rsync -avz hw0/ <unityID>@arc.csc.ncsu.edu:~/hw0/
Home directoryYour ~ is shared across the login and compute nodes — a file you build on arc is visible to your job.
Quotas & scratchHome space is limited. Put big or temporary data on scratch storage, not in ~, and clean up after a run.

Module 2 — Review

1. Which key do you register with ARC, and which never leaves your machine?

Register the public key (id_rsa.pub). The private key (id_rsa) stays on your laptop and is never shared.

2. You built a binary in ~/hw0 on the login node. Will your compute-node job see it?

Yes — your home directory is shared across login and compute nodes, so the job sees the same files.
Module 3
Software — Modules & Compilers

By the end you can…

  • Find and load software with environment modules
  • Compile an MPI, OpenMP, or CUDA program
  • Keep your toolchain reproducible across logins

Environment Modules

Why modulesThe cluster has many compiler / library versions. module load edits your PATH so the right tools appear — without conflicts.
Everyday module commands

module avail              # what's installed
module load cuda          # add CUDA toolchain
module load mpich         # add an MPI
module list               # what's loaded now
module unload cuda        # remove one
module purge              # start clean
Searchmodule avail 2>&1 | grep -i cuda finds a specific package (module writes to stderr).
ReproducibilityPut your module load lines in your job script, not just in your shell — so the job loads the same toolchain every time.

Compiling Parallel Programs

OpenMP (shared memory)

gcc -fopenmp \
    hello_omp.c -o hello_omp

Threads set by OMP_NUM_THREADS.

MPI (distributed)

module load mpich
mpicc hello_mpi.c -o hello_mpi

Launch with mpirun / srun.

CUDA (GPU)

module load cuda
nvcc hello.cu -o hello_cuda

Runs on a GPU compute node.

Load before you buildmpicc and nvcc only exist after the matching module load. "command not found" almost always means a missing module.
Module 4
Running Jobs

By the end you can…

  • Grab a node interactively with salloc
  • Write and submit a batch script with sbatch
  • Monitor a job and collect its output

Interactive Jobs — salloc

Best for debugging and quick tests: you get a shell on a real compute node and run commands by hand.

Allocate, run, release

salloc -N1 -n4 -p <partition>
# ... now you're on a compute node ...
module load cuda
./hello_cuda
squeue -u $USER          # see your job
exit                     # RELEASE the node
Flags-N = number of nodes, -n = number of processes/tasks, -p = partition / device.
Always exitAn allocation you forget to release keeps the node tied up and counts against you and your classmates.

Batch Jobs — a Job Script

job.sh

#!/bin/bash
#SBATCH -J hw0           # job name
#SBATCH -N 1             # nodes
#SBATCH -n 4             # tasks
#SBATCH -p <partition>   # partition
#SBATCH -t 00:10:00      # time limit
#SBATCH -o hw0.%j.out    # stdout (%j = jobID)
#SBATCH -e hw0.%j.err    # stderr

module load mpich
mpirun ./hello_mpi > result.txt 2>&1
Submit itsbatch job.sh → prints a jobID and returns immediately. The job runs when the scheduler finds room.

The #SBATCH lines are directives the scheduler reads; the rest is an ordinary shell script that runs on the compute node.

Monitor & Collect Output

Submit & watch

sbatch job.sh            # -> "Submitted batch job 12345"
squeue -u $USER          # PD pending, R running
scancel 12345            # kill it if needed

State PD = pending in queue, R = running. When it disappears from squeue, it finished.

Read the results

cat hw0.12345.out        # stdout
cat hw0.12345.err        # stderr
cat result.txt           # your program output
Cycleedit → compile → sbatch → squeue → read output → repeat.

Module 4 — Review

1. When would you use salloc instead of sbatch?

salloc for interactive debugging and quick tests (you type commands on the node); sbatch for unattended, repeatable, possibly long-running jobs that queue and write output to files.

2. Your job ran but produced no output. Where do you look first?

The #SBATCH -o / -e files (e.g. hw0.<jobID>.out / .err) — errors like a missing module load show up there.
Module 5
VS Code Remote (optional, recommended)

By the end you can…

  • Configure an SSH config file for ARC
  • Open the cluster's files directly in VS Code
  • Jump onto an allocated compute node from the editor

SSH config for ARC

Put this in ~/.ssh/config. It names the host, points to your key, and sets your Unity ID so you can just type ssh arc.

~/.ssh/config

Host arc
    HostName arc.csc.ncsu.edu
    IdentityFile ~/.ssh/id_rsa
    User <unityID>
Reach a compute nodeHop through the login node automatically with ProxyJump.
…also in ~/.ssh/config

Host c*
    HostName %h
    User <unityID>
    ProxyJump arc.csc.ncsu.edu
    IdentityFile ~/.ssh/id_rsa

%h = the host you typed (e.g. c39).

Connecting from VS Code

Install the extensionRemote - SSH (or the Remote Development pack, which adds WSL & tunnels). Either works.
  1. Set up ~/.ssh/config (previous slide).
  2. Allocate a node with salloc and note its name (e.g. c39).
  3. In VS Code press Ctrl/Cmd + Shift + P → "Remote-SSH: Connect to Host".
  4. Enter the node name (e.g. c39) — VS Code proxies through arc.
Why botherEdit, browse files, and use an integrated terminal on the compute node — no copying back and forth. Makes the edit/run loop much faster.
