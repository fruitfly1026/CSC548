Beyond CUDA — The Accelerator Landscape

One Problem, Many Silicon Answers

Every AI accelerator is chasing the same bottleneck we met with caches and GPUs: keep dense linear algebra fed. They converge on a small set of ideas — and differ mostly in how much they expose to you.

Matrix/tensor engineA hardware unit that does a small dense matmul per instruction — NVIDIA Tensor Cores, AMD Matrix Cores, Intel XMX, TPU MXU, Tensix FPU.
Explicit on-chip memoryBig SRAM scratchpads (shared memory, VMEM, L1) the program fills deliberately — locality you schedule, not just hope the cache finds.
Dataflow & scale-outSystolic arrays and tile grids stream operands between compute units; fast fabrics (Infinity Fabric, Xe-Link, ICI, Ethernet) stitch chips into pods.
The lock-in problemCUDA is proprietary and NVIDIA-only. Everyone else ships a portability layer so you don't rewrite kernels per vendor.

Vendor 1
AMD — CDNA, Matrix Cores & ROCm/HIP

Two Architectures: CDNA vs. RDNA

CDNA = Compute DNA (data-center) RDNA = Radeon DNA (graphics) CU = Compute Unit XCD = Accelerator Compute Die APU = CPU+GPU in one package
RDNA — graphicsOptimized for gaming/rasterization: high clocks, small wavefronts, large graphics caches. Runs the consumer Radeon line.
CDNA — computeAMD stripped the graphics fixed-function hardware (no ROPs/display) and spent the area on FP64/FP16 throughput, Matrix Cores, and HBM. This is the Instinct data-center line.

One design split, two markets — the same idea as NVIDIA splitting gaming GeForce from data-center Hopper/Blackwell.

Why the split mattersData-center AI/HPC cares about double precision and matrix throughput per watt, not pixels. CDNA is the branch this course cares about.

CDNA generations: CDNA 1 (MI100) → CDNA 2 (MI200/MI250X) → CDNA 3 (MI300X/MI300A) → CDNA 4 (MI350).

Matrix Cores & the Memory System

Matrix CoresAMD's answer to Tensor Cores: per-CU engines doing a dense tile MFMA (matrix fused multiply-add) each issue. CDNA 3 3× the FP16/BF16 and 6.8× the INT8 rate of CDNA 2, and adds FP8.
Infinity CacheA 256 MB shared last-level cache on MI300 — a big SRAM buffer that keeps HBM traffic (and its energy) down, exactly the locality lesson at chip scale.
Infinity FabricCoherent interconnect that links XCDs on-package and up to 8 GPUs into a node — up to 448 GB/s aggregate per GPU in an 8-way board.
MI300X: 8 XCDs over Infinity Fabric, 256 MB Infinity Cache, 192 GB HBM3.
Matrix Cores map 1:1 onto the tensor-engine theme. Infinity Cache is a huge SRAM last-level cache — the same "hold reuse in fast memory" idea we tiled for on CPUs.

The Software Story: ROCm & HIP

ROCm = Radeon Open Compute (stack) HIP = Heterogeneous-compute Interface for Portability hipify = CUDA→HIP source translator

ROCm is AMD's open GPU-compute stack — the counterpart to CUDA (compiler, runtime, libraries like rocBLAS / MIOpen, the analog of cuBLAS / cuDNN).

HIP is a C++ dialect deliberately near-identical to CUDA: __global__ kernels, <<<grid,block>>>-style launches, threadIdx. The same HIP source compiles for both AMD (ROCm) and NVIDIA (CUDA).

Portability playExisting CUDA code is mechanically translated (hipify) — most kernels port with light edits, breaking the single-vendor lock-in.
CUDA vs. HIP — near mirror image

// CUDA                    // HIP
__global__ void add(       __global__ void add(
  float* c, ...) {           float* c, ...) {
 int i = blockIdx.x*        int i = blockIdx.x*
   blockDim.x+threadIdx.x;    blockDim.x+threadIdx.x;
 c[i]=a[i]+b[i]; }          c[i]=a[i]+b[i]; }

add<<<g,b>>>(c,...);       hipLaunchKernelGGL(
                             add,g,b,0,0,c,...);
// cudaMalloc / cudaMemcpy  // hipMalloc / hipMemcpy

The names differ by a prefix; the programming model is the same SIMT grid-of-blocks you already know.

ROCm/HIP: AMD ROCm documentation; HIP portability & hipify.
Key contrast with Intel/Google: AMD's portability strategy is "make it look exactly like CUDA," whereas Intel bets on the open SYCL standard and Google hides everything behind XLA.
Vendor 2
Intel — Xe, XMX & oneAPI/SYCL

The Xe Family & Ponte Vecchio

Xe = Intel's GPU architecture family Xe-HPC = data-center variant PVC = Ponte Vecchio (Data Center GPU Max) Xe-core = compute unit

Intel's Xe is one architecture, scaled across markets: Xe-LP (integrated), Xe-HPG (gaming Arc), and Xe-HPC for the data center.

Xe-HPC = "Ponte Vecchio", sold as the Intel Data Center GPU Max (e.g. Max 1550). It powers the Aurora exascale supercomputer.

  • Up to 128 Xe-cores across two stacks
  • Xe-core = 8 vector engines + 8 XMX matrix engines + shared local memory
  • Up to 128 GB HBM2e; Xe-Link stitches 8 GPUs together
An engineering extremePVC packs >100 billion transistors across 47 active tiles on 5 process nodes (Intel 7, TSMC N5/N7) in one package.
Status noteIntel later narrowed its data-center GPU roadmap (Max 1350 cut; "Falcon Shores" repositioned). PVC still matters as an architecture — and Aurora runs on it.
Intel Xe GPU Architecture (oneAPI optimization guide); Data Center GPU Max 1550 product spec; 47 tiles / 100B+ transistors.
Don't oversell current market position; teach the architecture. The 47-tile package is the most aggressive chiplet integration shipped — a great contrast with AMD's cleaner 8-XCD approach.

XMX — Systolic Matrix Engines & Advanced Packaging

XMX = Xe Matrix ExtensionsPer-Xe-core systolic matrix engines (Intel's Tensor/Matrix-Core analog). A full PVC has 1024 XMX engines alongside 1024 vector engines, feeding on FP16/BF16/INT8.
EMIB — 2.5DEmbedded Multi-die Interconnect Bridge: a tiny silicon bridge in the substrate links tiles edge-to-edge (e.g. compute ↔ HBM) without a full interposer.
Foveros — 3DStacks compute tiles vertically on a base die — active-on-active 3D integration. PVC uses both EMIB and Foveros.
EMIB links tiles side-by-side; Foveros stacks them; XMX = systolic matrix engines.
XMX is systolic — a natural bridge to the TPU section, where we make "systolic" concrete. EMIB vs Foveros = 2.5D vs 3D; both appear in one PVC package.

The Software Story: oneAPI & SYCL

oneAPI = Intel's open cross-arch programming model SYCL = Khronos single-source C++ for heterogeneous compute DPC++ = Intel's SYCL compiler oneMKL/oneDNN = math / DNN libraries

SYCL is an open Khronos standard: single-source, standard C++ (no language extensions) with kernels written as lambdas. It targets Intel, NVIDIA, and AMD GPUs — vendor-neutral by design.

oneAPI is Intel's implementation + libraries (oneMKL, oneDNN, oneCCL) with the DPC++ compiler. A SYCLomatic tool migrates CUDA → SYCL.

Different bet than HIPAMD mirrors CUDA's syntax; Intel pushes an ISO-C++-based open standard. Same goal — write once, run on many vendors' accelerators.
SYCL — single-source C++ (submit a kernel)

queue q;                       // pick a device
q.submit([&](handler &h) {
  h.parallel_for(range<1>(N),
    [=](id<1> i) {
      c[i] = a[i] + b[i];      // kernel body
  });
}).wait();
// buffers/USM move data; same
// source compiles for Intel,
// NVIDIA, and AMD back-ends

Host and device code live in one file; the runtime picks and dispatches to a device.

oneAPI/SYCL: Intel oneAPI Optimization Guide; Khronos SYCL specification.
SYCL is the open-standard route; students who know CUDA will find the parallel_for/lambda model familiar. Emphasize "single source" — no separate .cu compilation model.
Vendor 3
Google TPU — Systolic Arrays at Datacenter Scale

A Domain-Specific Chip

TPU = Tensor Processing Unit MXU = Matrix Multiply Unit (systolic) VPU = Vector Processing Unit ICI = Inter-Chip Interconnect bf16 = bfloat16

The TPU is an ASIC built for one job: the dense matmuls inside neural networks. Not a general GPU — no rasterization, minimal control logic, area spent on multiply-accumulate.

Design betNeural nets are overwhelmingly matrix multiply. Build a giant hardwired matmul engine (the MXU) and a simple in-order pipeline around it.
TensorCore = 3 unitsMXU (systolic matmul) · VPU (elementwise / activations) · scalar unit (control + DMA). Fed by on-chip VMEM scratchpad, backed by HBM.
bfloat16 — Google's format16-bit with the same 8-bit exponent as FP32 (just fewer mantissa bits). Same dynamic range → drop-in for training without loss scaling.
Multiply cheap, accumulate safeMXU multiplies in bf16 but accumulates in FP32 — throughput of 16-bit, numerical stability of 32-bit.
bfloat16 is one of the TPU's most influential contributions — now everywhere (including NVIDIA/AMD). The "TensorCore" here is Google's whole core, not to be confused with NVIDIA's Tensor Core unit.

The Systolic MXU — How Data Flows

Systolic array: weights stay put, activations march left→right, partial sums accumulate top→bottom.

A systolic array is a grid of tiny multiply-accumulate cells. Data pulses through (like a heartbeat — "systole"):

  • Weights are loaded once and held stationary in each cell
  • Activations stream in from the left, one column per cycle
  • Each cell does one multiply-add and passes operands on
  • Partial sums flow down, emerging as finished results
Why it's efficientEach operand is reused across the whole array after a single memory fetch — no register-file or cache traffic per MAC. Data movement, the usual bottleneck, is nearly eliminated.

MXU = 128×128 array (16,384 MACs) through v5p; 256×256 on v6e/Trillium.

This is the conceptual heart of the topic. Contrast with a GPU: a GPU streams operands through register files and shared memory every step; the systolic array wires the reuse into the datapath so operands move directly cell-to-cell. Hong & Kung's systolic idea (1978) finally in mass production.

Pods, ICI & the XLA Compiler

ICI — the on-fabric NoC, between chipsDedicated high-speed links wire chips directly into a 2D torus (v5e/v6e) or 3D torus (v4/v5p) — no host or NIC in the path. A torus-connected set of chips is a slice; a full assembly is a pod.
Why a torusWrap-around links bound the hop count and give all-reduce (the key training collective) short, uniform paths — the same topology reasoning from the interconnects unit.

v5p: 96 GB HBM/chip, ~2.8 TB/s; ~459 bf16 TFLOP/s per chip; ~4.1 EFLOP/s per 8960-chip pod.

XLA — you never write a kernelYou write JAX / TensorFlow / PyTorch; the XLA compiler lowers the whole graph to TPU code — fusing ops, choosing tile layouts, and inserting ICI collectives for you.
The portability contrastNo CUDA, no HIP, no SYCL exposed. Google's answer to lock-in is a graph compiler: target the framework, let XLA own the hardware. Great for productivity, less for hand-tuning.

Same JAX program scales from 1 chip to a full pod — sharding is a compiler/annotation concern.

TPU architecture & ICI (Google Cloud docs); "How to Scale Your Model" (JAX) TPU chapter for per-chip/pod figures.
Tie ICI/torus back to the interconnects lecture (torus, bisection bandwidth, all-reduce). XLA is the philosophical opposite of TT-Metalium: maximum abstraction vs. bare metal.

Module 1
Tenstorrent Architecture

What Is a Dataflow Architecture?

Control-flow (von Neumann)A program counter walks through instructions in order. Computation is driven by the instruction stream; data is fetched on demand. This is what a CPU — and a classic multicore — does.
DataflowComputation is driven by the availability of data. The program is a graph of operations wired by data dependencies; an operation “fires” when its operands arrive and data flows through the fabric — no single global PC orders everything.

Classic dataflow machines (MIT Tagged-Token, Manchester, 1980s): an operation fires when its tokens (operands) are ready.

Modern spatial dataflow accelerators map the computation graph onto a grid of compute tiles; data streams tile-to-tile over an on-chip network. Examples: Tenstorrent, systolic arrays / TPU, Groq, Cerebras, SambaNova.

Tenstorrent is dataflowThe reader → compute → writer pipeline with circular buffers is dataflow in miniature: a tile flows in, the compute kernel fires when its input buffer holds tiles, the result flows out — replicated across the whole grid.

Design Philosophy: A Grid, Not a Hierarchy

Tenstorrent is a throughput AI accelerator built from a homogeneous grid of Tensix cores on a 2-D Network-on-Chip (NoC). Work is expressed on 32×32 tiles, not scalars.

  • No cache hierarchy — a deliberate choice. There is no L2/L3, no coherence protocol.
  • Instead: large distributed SRAM, directly addressable across the chip — any component can read any core's SRAM over the NoC.
  • Data movement is explicit and programmer-controlled, never implicit caching.
Why drop caches?Caches spend area and power guessing reuse. For dense tensor work the reuse pattern is known, so the programmer schedules it directly.
Grid of Tensix cores + NoC, backed by device DRAM, with Ethernet links at the edges.

No Cache: Distributed SRAM over the NoC

The tradeA CPU/GPU hides the memory hierarchy behind caches and coherence. Tenstorrent exposes a flat sea of SRAM over the NoC — more programmer work, but full control and no coherence overhead.

Inside One Tensix Core

  • 5 "baby" RISC-V cores: RV 0 = data-in / reader, RV 4 = data-out / writer, RV 1–3 drive the compute engine
  • Compute engine, 3 units: FPU = matrix engine (32×32 tile matmul), SFPU = vector engine, ThCon = scalar / packer-unpacker
  • 2 NoC routers — two independent NoCs for L1 ↔ DRAM ↔ neighbor traffic
  • ~1–1.5 MB local SRAM (L1) — no per-core cache
Division of laborThree kernel roles (reader / compute / writer) map onto distinct RISC-V cores running concurrently.

The Grid & the 2-D Torus NoC

A device is a 2-D grid of elements — e.g. roughly 10×12 on Wormhole, of which ~80 are designated Tensix compute cores (the rest are DRAM, Ethernet, and PCIe tiles).

  • A 2-D torus NoC wraps edges so traffic has no dead ends
  • It moves tiles between cores and between cores and DRAM
  • Every core can reach any SRAM on the chip — the basis for Lab 2's multi-core split and reuse patterns
Two NoCsThe two routers per core form two independent NoCs, so reads and writes can use separate networks and run in opposite directions.
Cores wired by a torus NoC; red dashed = wrap-around edges.

Ethernet Scale-Out & Galaxy

Starting with Wormhole, each chip carries 16 × 100 Gb Ethernet ports. Chips link directly into large 2-D meshes — the on-chip NoC effectively extends across chips.

  • A core on one chip can stream tiles to a core on another over Ethernet
  • Many chips combine into "Galaxy" systems for very large models
  • Philosophy: scale OUT with commodity links, not a single giant die
One programming model, many scalesThe same tile + NoC abstraction spans a single core, a full chip, and a multi-chip Galaxy.

Tiles & Matmul as Tile Accumulation

Tensix hardware operates on 32×32 tiles. A matrix is reshaped into a grid of tiles:

\( M_t = M/32,\quad K_t = K/32,\quad N_t = N/32 \)

Each output C-tile is a sum of tile-products along K:

\( C_{mt,nt} = \sum_{kt=0}^{K_t-1} A_{mt,kt}\, B_{kt,nt} \)
  • A tile (bf16) = \( 2 \times 32 \times 32 = 2048\) bytes; tiles stored row-major
  • A index = mt*Kt + kt; B index = kt*Nt + nt
Inner loop over kt accumulates into one register tile.

The Programming Stack

The Layered Stack

Higher layers are more automated; lower layers give more control.

  • TT-Forge / TT-MLIR — compile whole models, no kernels written
  • TT-NN — call optimized ops from Python
  • TT-Metalium — write kernels by hand labs
  • Hardware — the Tensix grid
All open sourceThe entire stack is open and RISC-V-based — you can read every layer down to the kernels.

Layer: TT-Metalium

The low-level, open-source C++ SDK — bare-metal direct access to the hardware. This is what the labs use.

  • Direct control of RISC-V cores, the NoC, and the matrix / vector engines
  • Explicit memory & data movement — you place buffers and circular buffers yourself
  • You write reader / compute / writer kernels plus a host program
  • TT-LLK — a low-level kernel library of compute primitives sits just beneath it
AnalogyTT-Metalium is to Tenstorrent roughly what writing CUDA kernels (or even PTX) is to a GPU — but with the data movement fully exposed.
Why teach at this levelDropping to Metalium forces you to confront tiles, circular buffers, the NoC, and core placement directly — the whole point of the labs.

Layer: TT-NN

A Python + C++ operator library of pre-packaged, optimized ops, built on top of Metalium.

  • PyTorch-like API — tensors, ops, and modules feel familiar
  • Run models without writing kernels — the optimized kernels already exist underneath
  • Each op ultimately calls hand-tuned Metalium / TT-LLK code
Where most users liveIf you just want to run a model fast, TT-NN (or TT-Forge above it) is the normal entry point — not raw Metalium.

Layer: TT-Forge / TT-MLIR Compiler

An MLIR-based compiler that ingests models from PyTorch, JAX, and TensorFlow and lowers them automatically — no custom kernels needed.

  • Dialects: TTIR → TTNN / TTKernel
  • Optimization passes: operator fusion, sharding across cores, and layout (tiling) selection
  • Finally lowers to TT-Metalium
The automated pathTT-Forge is the general, hands-off route: bring a trained model, get it running on the grid.

Lab 1
Single-Core Matmul

The Problem & the Tiled Idea

Compute C = A · B on one Tensix core:

\( A_{640\times320}\cdot B_{320\times640} = C_{640\times640} \)
  • With 32×32 tiles: Mt=20, Kt=10, Nt=20
  • One core produces all \(M_t\cdot N_t\) output tiles
  • Each output tile accumulates over Kt tile-products
Three kernels, one core
  • reader — streams A & B tiles DRAM → CBs
  • compute — tile matmul + accumulate → output CB
  • writer — output CB → DRAM
Loop tiling = localityTiling turns a giant matmul into many small ones that fit in fast L1 — the same idea as blocking for cache.

Circular Buffers & the Reader → Compute → Writer Pipeline

Circular buffer (CB)A FIFO queue in L1 connecting a producer and consumer kernel. Sized 2 * tile_size for double-buffering.
  • reader: DRAM → CB (cb_reserve_back → push)
  • compute: CB → engine → CB (wait_front / pop)
  • writer: CB → DRAM

CB indices by convention: cb_src0=0, cb_src1=1, cb_output=16.

Host API Lifecycle — Device & Buffers

TT-Metalium host (C++)

// 1. Open a device and get its command queue
auto mesh_device = MeshDevice::create_unit_mesh(device_id);
auto& cq = mesh_device->mesh_command_queue();

// 2. Tile dimensions
uint32_t Mt = M / TILE, Kt = K / TILE, Nt = N / TILE;
uint32_t tile_size = sizeof(bfloat16) * TILE * TILE;   // 32x32

// 3. DRAM buffers for src0, src1, dst
DeviceLocalBufferConfig dram_cfg{.page_size = tile_size,
                                 .buffer_type = BufferType::DRAM};
auto src0 = MeshBuffer::create(dram_cfg, /*...*/, mesh_device.get());

auto dst  = MeshBuffer::create(dram_cfg, /*...*/, mesh_device.get());

create_unit_mesh gives a single-device mesh; the command queue serializes host→device work.

Compute Kernel — Tile Matmul

mm.cpp — compute kernel (C++)

mm_init(cb_in0, cb_in1, cb_out);

for (uint32_t mt = 0; mt < Mt; mt++) {
  for (uint32_t nt = 0; nt < Nt; nt++) {
    tile_regs_acquire();                 // own the dst register tile
    for (uint32_t kt = 0; kt < Kt; kt++) {
      cb_wait_front(cb_in0, 1);          // A tile ready
      cb_wait_front(cb_in1, 1);          // B tile ready
      matmul_tiles(cb_in0, cb_in1, 0, 0, 0);  // C += A_kt * B_kt
      cb_pop_front(cb_in0, 1);
      cb_pop_front(cb_in1, 1);
    }
    tile_regs_commit();                  // hand dst to packer
    tile_regs_wait();
    pack_tile(0, cb_out);                // dst tile -> output CB
    cb_push_back(cb_out, 1);
    tile_regs_release();
  }
}

The inner kt loop accumulates into a single register tile before packing it out.

Lab 2
Multi-Core Matmul (SPMD)

SPMD: Static Work Assignment

The single core's output tiles are now partitioned across many cores. Each core runs the same kernels on its own slice of output tiles.

No dynamic schedulingUnlike a GPU's block scheduler, each core gets a fixed set of tiles at launch. A core that finishes early simply idles until the next launch — there is no oversubscription or work-stealing.
Each core owns a fixed range of output tiles.

split_work_to_cores() & Uneven Splits

split_work_to_cores() distributes the \(M_t\cdot N_t\) output tiles across the available cores, returning:

  • The number of cores to use
  • Two core groups (primary / secondary) for uneven splits
  • The work-per-core for each group
Example81 output tiles across 11 cores → 4 cores × 8 tiles + 7 cores × 7 tiles (32 + 49 = 81). The two groups differ by one tile — as even as possible.
host (C++)

auto [num_cores,
      all_cores,
      core_group_1,   // primary
      core_group_2,   // remainder
      work_per_core_1,
      work_per_core_2] =
    split_work_to_cores(grid, Mt * Nt);

Two groups so an uneven split needs no per-core branching at runtime.

Per-Core Runtime Args Over Core Ranges

host (C++)

uint32_t work_offset = 0;
for (auto& [group, work_per_core] : {std::pair{core_group_1, work_per_core_1},
                                     std::pair{core_group_2, work_per_core_2}}) {
  for (const CoreCoord& core : corerange_to_cores(group)) {
    SetRuntimeArgs(program, reader,  core,
        {src0->address(), src1->address(), Mt, Kt, Nt, work_offset, work_per_core});
    SetRuntimeArgs(program, compute, core, {work_per_core});
    SetRuntimeArgs(program, writer,  core,
        {dst->address(), work_per_core, work_offset});
    work_offset += work_per_core;        // next core's start tile
  }
}
What the kernels receive Each kernel takes a tile range: a start tile id (work_offset) and a count (work_per_core). The reader uses modulo arithmetic on the start id to recover row/col; the compute outer loop is bounded by the count (inner kt loop unchanged); the writer offsets its DRAM writes.

Two Axes That Explain Everything

Axis 1 — who moves the data?Along a spectrum from implicit (CPU/GPU caches) to explicit (TPU VMEM, Tenstorrent SRAM). The more the hardware hides, the easier to program; the more it exposes, the more peak you can extract.
Axis 2 — how portable is your code?From locked-in (CUDA) through source-portable (HIP, SYCL) to compiler-abstracted (XLA, TT-Forge). You trade hand-tuning control for freedom to move between vendors.
The unifying lessonEvery one of these machines is a throughput accelerator bounded by data movement. The parallel-programming skills from this course — tiling for locality, SPMD work-splitting, keeping engines fed, reasoning about interconnect topology — transfer directly to all of them.
Practical takeawayLearn the portability layer first (HIP, SYCL, XLA) to be productive; drop to the bare-metal layer (CUDA, Metalium) only where the last factor of performance actually matters.

You can now place any new accelerator on these two axes and predict how you'd program it.

Close by pointing back to the Tenstorrent labs: they are the "explicit + bare-metal" corner of both axes, which is exactly why they teach the hardware so effectively. The SpMV/CUDA comparison later revisits the implicit end.
